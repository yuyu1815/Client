# Boss client particle source evidence (Java 26.2)

This module recreates only client-local `Level.addParticle` visuals. Dragon server AI/flight target and Wither combat AI are not ported. Explicit `ServerLevel.sendParticles` output remains owned by the packet path and must not be duplicated here.

| Java source and behavior | Rust owner / equivalent |
|---|---|
| `world/entity/boss/enderdragon/EnderDragon.java`, `aiStep`: records 64-entry `flightHistory`; on the client calls phase `doClientTick`; separately computes head/neck/body/tail/wing `EnderDragonPart` positions through `tickPart` and `getHeadYOffset`. | `entity/particle_bosses.rs::tick_boss_particles` owns per-entity position/yaw history; first sample initializes 64 slots and subsequent client ticks shift one sample. `dragon_head` reconstructs Java head coordinates using history delays 0/5/10, phase sitting offset, and synchronized transform. It does not port server flight AI. Body/neck/tail/wing part coordinates are not needed by these local particle call sites. |
| `EnderDragon.DATA_PHASE`, `EnderDragon.onSyncedDataUpdated`, and `EnderDragonPhase` constants (Landing=3, SittingFlaming=5, SittingScanning=6, SittingAttacking=7, Dying=9, Hovering=10). | `EntityStore::apply_entity_data` metadata index 16 updates/resets `BossParticleState::dragon_phase`, phase ticks, and death ticks; `tick_boss_particles` dispatches only on the synced phase. Invalid Java phase IDs fall back to phase 0 (HoldingPattern). |
| `phases/DragonLandingPhase.java::doClientTick`: 8 Gaussian samples around `dragon.head` each client tick, DRAGON_BREATH power 1, velocity from head look and dragon movement, look yaw fan rotated -π/4 then by π/16. | `dragon_breath(..., sitting=false)` emits eight `Kind::DragonBreath` requests with `Options::Power { power: 1.0 }`; head location from `dragon_head`, movement from synchronized entity velocity. |
| `phases/DragonSittingFlamingPhase.java::doClientTick`: increments local `flameTicks`; on even ticks <10, 8 Gaussian head samples and six breath particles per sample. | `dragon_breath(..., sitting=true)`; `dragon_phase_ticks` resets on metadata transition and gates 48 requests on client phase ticks 2,4,6,8. `AreaEffectCloud` from the separate server attack is not duplicated. |
| `phases/DragonDeathPhase.java::doClientTick`: increments local time and emits one `EXPLOSION_EMITTER` every 10 ticks with x/z spread 8 and y spread 4 around dragon +2. `EnderDragon.aiStep` also locally adds one `EXPLOSION` while dead, with same offsets. | `tick_boss_particles` emits `ExplosionEmitter` at the 10-tick cadence and `Explosion` while health is zero, with Java spread and emitter kind. Neither is `ServerLevel.sendParticles`. |
| `world/entity/boss/wither/WitherBoss.java::aiStep`: updates two secondary head yaw/pitch toward synchronized alternative target IDs; emits 3 head-position SMOKE particles, powered head aura at 1/4 probability, and 3 invulnerability aura particles every client tick. `getHeadX/Y/Z` puts side heads at ±1.3 around body yaw, y+2.2; center at y+3.0. `isPowered` is health <= max/2. | `tick_wither` resolves target IDs against `EntityStore::living`, interpolates secondary head rotations, samples three distinct Java head positions, emits smoke / colored `EntityEffect`, and uses health and synchronized invulnerability. Missing targets follow Java's body-yaw fallback; their retained IDs are not cleared. |
| `WitherBoss.DATA_TARGET_A/B/C`, then `DATA_ID_INV`, after `Mob`'s single metadata byte (15). `Monster` defines no synchronized data, so Java indices are target IDs 16,17,18 then invulnerability 19. | `EntityStore::apply_entity_data` stores targets at 16..18 and invulnerability at 19. Target slot 0 is retained too (Java's center head doesn't use it for the secondary-head look update). |

`EntityStore` holds `boss_particle_state`; `spawn_living` clears stale state on ID reuse and `remove_entity` removes it. Integration entry point is `entity::particle_bosses::tick_boss_particles(&mut EntityStore, &ChunkStore, game_time) -> Vec<ParticleSpawnRequest>`. It is callable from the later aggregate; `last_tick` prevents duplicate output for repeated calls at one game time. No core/app dispatch was edited here.
