# Particle complete-coverage plan (native Java 26.2)

> **Latest implementation/verification snapshot:** see [`particle-integration-verification.md`](particle-integration-verification.md). The plan and baseline/design text below records why the work was scoped and how Java behavior was assigned to owners; it is not a current list of unimplemented code. Latest snapshot: `mise run check` and serial `mise run test` both exit 0; client 1,766 / protocol 52 pass; GUI/GPU comparison, screenshot particle identity, custom biome visual lightmap overrides, and some custom composite item selectors remain unverified or unsupported.

## Goal and completion boundary

Implement complete Minecraft Java 26.2 particle coverage in Rust: all 125 native particle registry entries, their wire options, provider behavior, ticking/collision/tracking/emitter behavior, rendering and assets, and every Java natural/event-driven occurrence that is applicable to the Rust client's supported game state. “Registered”, “packet decoded”, or “a sprite exists” alone is not completion.

The canonical type set is the ordered `particle_type` registry in `pomme-protocol/src/data/registries-26.2.json` (protocol 776), cross-checked against `third_party/SteelMC/steel-registry/build_assets/particle_types.json`. Java provider references are in `minecraft-26.2-decompiled/src/net/minecraft/client/particle/ParticleResources.java`; Java runtime and particle implementation references are in the same decompile tree. Per-type tracking is in `particle-registry-ledger-26.2.csv`; the Java generation-callsite inventory and semantic review are in `particle-java-callsite-inventory-26.2.csv` and `particle-java-callsite-source-audit-26.2.md`.

Native Java 26.2 is the particle behavior/registry baseline. The client also lists protocol connections from 1.20 through 26.3 in `pomme-protocol/src/version.rs::VERSIONS`. Keep those connections working by translating each listed source protocol's particle IDs and option layouts into the native representation; do not expand this project into unlimited historical/future particle registries. Same-protocol version labels use the repository's embedded protocol tables. New protocol versions beyond this list, and their registry additions, are outside this plan unless separately requested.

## Chosen design and ownership

- **Network boundary (`pomme-client/src/net/handler.rs`, `net/translate.rs`)** owns source-protocol framing, version-specific particle ID/option translation, exact payload consumption, and rejection of unknown/malformed data. Translation must produce the canonical native particle kind plus typed options; packet code must not guess that an unknown option is empty/simple.
- **Particle subsystem (`pomme-client/src/particle.rs`)** owns typed spawn requests, provider-equivalent per-kind initialization, particle-instance state, tick/physics/collision, lifetime, tracking attachment and emitters, and render-ready extraction consumed by `renderer/pipelines/particle.rs`. Reuse the existing `ParticleStore` and renderer. Do not port Java's class hierarchy or create a second generic particle engine.
- **Gameplay state owners** own occurrence conditions: the block/fluid state and client-world tick own block/fluid/ambient events; entity/projectile update owners own entity-state occurrences; interaction/network event handlers own event occurrences; weather/biome state owners own precipitation/weather occurrences. These owners send typed spawn requests to the particle subsystem. Do not accumulate a giant condition switch in `in_game.rs` or `particle.rs`.
- Reuse Rust's existing block/chunk/entity/weather/event state and particle mechanics. If a Java source requires state or simulation that Rust does not currently expose, list that as an explicit dependency in the ledger and implement that game mechanism in its owner before marking the corresponding natural occurrence complete. Do not import Java architecture merely to mimic class names.

## Phases

Phases 3–5 may proceed concurrently where their inputs are available, but no phase or subset is a final coverage claim. Every unresolved ledger row and occurrence remains open until closed.

1. **Registry/provider/occurrence baseline.** This was the investigation phase. The current CSV now preserves **146 source rows / 303 candidates**, with per-callsite semantics and current path rechecks; the original 286/144 search result is only the superseded extraction baseline, not the final source denominator. The full meaning/status distinction is documented in `particle-java-callsite-source-audit-26.2.md`.
2. **Type/ID/codec/translation correctness.** Replace/repair hand-maintained ID drift at the registry ownership boundary; make registry-to-kind coverage mechanically testable; decode all typed options exactly; translate every supported source protocol into native 26.2 IDs/options. Add tests for every type/codec boundary, source-version layout, truncation/unknown IDs, exact cursor consumption, and regression of existing network paths. No option-bearing kind may fall through as simple.
3. **Shared tick/render foundations and ordinary providers.** Compare Rust shared particle mechanics and render path with Java `Particle`, `ParticleEngine`, `ParticleResources`, particle groups, resources and atlas definitions. Close any common deficits, then implement all ordinary provider types including their per-kind init, sprite, animation, color/light/alpha, lifetime and motion. A generic fallback is not a substitute for provider parity.
4. **Special options, tracking, emitters and rendering.** Implement every remaining kind, including block/item-state option providers, color transitions, entity/block vibration targets, trail, shriek, falling/dust variants, special render groups/no-render behaviors, and emitters/child particles. Compare Java special providers, `TrackingEmitter`, group behavior and `ParticleEngine` scheduling. If the provider is ordinary, it should already be closed in phase 3; phase 4 is not permission to omit any type.
5. **Natural and event-driven production plus missing game state.** Implement all relevant Java generation sources in their owning Rust block/fluid/entity/item/interaction/weather/environment/event state code. Include server packet and entity-event paths as well as local client effects. Add missing gameplay/world state as dependency work where required; do not close naturally occurring particles by implementing only packet reception. The ledger must identify the Java source and matching Rust trigger or document, with evidence, that Java has no natural source for that type.
6. **Full closure and Java comparison.** Run the complete 125-kind registry/codec/provider audit, supported-protocol translation tests, occurrence inventory audit, and automated tests. Compare Java and Rust visual and temporal behavior for representative and special cases using deterministic inputs where possible. Perform in-game comparison for all feasible kinds and their important trigger paths; if a real-client comparison cannot be performed, mark those cells `未検証` and do not claim full parity. Completion requires zero `未調査`/`未実装` ledger cells or occurrence records and passing automated checks. The initial screenshot's particle type is still unknown; resolving that original symptom is a separate verification item and is not implied by general coverage.

The sampler's recovery and state inputs are documented in `particle-block-sampler-recovery.md`; follow-up evidence and remaining uncertainty are summarized in the current integration verification.
- The current reviewed source inventory has **146 Java source rows / 303 extracted candidates / 254 generation operations / 49 declarations, helpers, delegations or no-client sources**. ## Verification and completion gate

1. Registry test: native 26.2 names and IDs 0–124 match exactly; each registry entry resolves to exactly one typed implementation/provider record; no duplicates, missing variants or wrong aliases.
2. Codec/translation tests: each option codec consumes exactly its schema; native and every distinct wire layout among supported source protocol tables are tested; round-trip/translation preserves kind and option meaning; unknown/malformed data is rejected safely.
3. Spawn/provider tests: each of the 125 rows reaches the correct provider initialization from a typed request and has tested behavior parameters/asset selection. Include child/emitter and tracking attachment lifecycle tests where applicable.
4. Tick/render tests: test lifetime, motion, collision, animation, tint/light/alpha, render grouping and special behavior appropriate to each provider. Existing tests for a neighboring/common particle do not close a row by analogy.
5. Occurrence tests: every reviewed Java source occurrence is mapped to an implemented Rust trigger or evidence-backed “no natural trigger”; relevant state dependencies are complete and tested. Verify at least block/fluid ambient loops, entity/projectile state triggers, item/interaction and event paths, and weather/biome/environment conditions where Java uses them.
6. In-game comparison: compare deterministic/specific packet spawns and naturally triggered examples against Java 26.2. Record reference, trigger, options, approximate trajectory/lifetime, visual result, and pass/fail. Any impossible-to-execute case remains `未検証`, not passed.
7. User symptom follow-up: identify the actual screenshot particle and reproduce it separately; successful generic suite coverage does not by itself establish that this unnamed symptom is fixed.

## Natural/event occurrence investigation: implementation units

The companion `particle-java-callsite-inventory-26.2.csv` preserves the original 146 source rows and summarizes the latest 303 structured callsite records. The original 286/144 search result was only an early mechanical candidate scan and is superseded. Server `sendParticles` operations remain packet-owned; API declarations, helpers and no-ops are not client source gaps. Per-record audit completion does not certify provider fidelity or a test/visual result.

### Recommended world/block/fluid sampler

Implement the sampled, client-local world effects in one narrow world-owned unit (e.g. `world/particle_tick.rs`, name is an implementation choice) called from the fixed client/world tick in `app/phases/in_game.rs::update_game`, adjacent to the existing campfire scan and before `ParticleStore` ticking (`in_game.rs:3496`, `3694–3803`). It must model Java `ClientLevel.animateTick` / `tickWeatherEffects`, **not server random ticks**: Java calls `ClientLevel.animateTick` from client `Minecraft.runTick` (`minecraft-26.2-decompiled/src/net/minecraft/client/Minecraft.java:1918–1920`); `ClientLevel.animateTick` samples local positions and calls block/fluid `animateTick`, drip and ambient attributes (`ClientLevel.java:568–670`); rain sampling is a separate client weather method (`ClientLevel.java:359–399`). Do not port server block random-tick/gameplay behavior.

Suggested narrow contract: accept an immutable snapshot/access to `ChunkStore`, biome climate map, `SkyState` / `DimensionEnvironment`, current camera/player sample origin, current client tick/particle status, and a reproducible random source; return a bounded `Vec<ParticleSpawnRequest>` (typed kind/options, position/velocity, and visibility/limiter flags). `update_game` forwards those requests to `ParticleStore`. The sampler does not retain particle lifetimes or implement provider/tick/render behavior; `ParticleStore` remains owner of live instances only. Avoid an all-world scan: sample the loaded client neighborhood around the camera as Java does.

Most spatial inputs are already available: block state and loaded chunks in `world/chunk.rs::ChunkStore` (`chunk.rs:127–133, 291–303`); motion-blocking heightmap (`chunk.rs:340–354`); biome palette IDs (`chunk.rs:357–372`) and per-ID `BiomeClimate` (`renderer/chunk/mesher.rs:444–448`, populated from registry data in `net/connection.rs:1287–1330`); fluid kind/amount/falling derived from block state (`world/block/mod.rs:84–121, 742–767, 1025–1026`); and static local block shape lookup (`world/block/mod.rs:1037–1038`). Rust already renders rain/snow columns via `renderer/pipelines/weather.rs::precipitation_for` and `in_game.rs:6411–6418`, and keeps weather intensity in `SkyState` (`renderer/pipelines/sky.rs:115–119`) updated by `core.rs:4135–4143`. What is missing is the Java-like random sample loop that creates local impact particles (including RAIN vs SMOKE based on sampled surface/fluid) and block/fluid animate callbacks; weather mesh rendering is not a replacement for those particle events.

`EnvironmentAttributes.AMBIENT_PARTICLES` is read by Java `ClientLevel.doAnimateTick` (`ClientLevel.java:621–628`), but no ambient-particle attribute storage/decoder was found in Rust (`rg ambient_particle` returned only environment/fog references). This is an actual received-or-unimplemented data dependency: establish how native 26.2 server datapack/registry values reach the client, retain the applicable ambient definitions/probabilities, and feed them to the world sampler. Do not fabricate a generic smoke fallback. Weather already has a precipitation mesh, but only a fixed `WEATHER_RADIUS=10` was found (`renderer/pipelines/weather.rs:14–17`); Java client rain particle count also uses the `weatherRadius` setting and `ParticleStatus` (`ClientLevel.java:359–399`). Check whether the client option is retained elsewhere before deciding whether matching its setting behavior requires new menu state. Block-entity state likewise differs by type: raw NBT is kept in `StoredBlockEntity` (`world/block_entity.rs:27–44, 178–187, 230–238`), while only selected presentation fields/timers are parsed (campfire slots, bell swing, enchanting book, pot wobble); the fixed tick explicitly updates book/bell and has a bespoke campfire scan (`in_game.rs:3670–3750`). `BaseSpawner`, `TrialSpawner`, `Vault`, `Conduit`, `CreakingHeart`, and `PotentSulfur` client particle tick state is not represented by a general BE visual-tick dispatcher. Keep raw NBT when sufficient; add only the exact derived, synced/config/timer fields required by each source owner, and route server-sent effects through packets rather than reproducing them.

### Event and entity source ownership

- **Server `sendParticles`** is already authoritative: Java `ServerLevel.sendParticles` creates and sends `ClientboundLevelParticlesPacket` (`server/level/ServerLevel.java:1141–1166`), parsed as `NetworkEvent::LevelParticles` (`pomme-client/src/net/handler.rs:2627–2778`, event shape `net/mod.rs:611–625`) and dispatched to `ParticleStore` in `app/core.rs:4500–4520`. Implement these sites through packet/codec coverage only; do not locally spawn the same server-sent effect. Source rows in the CSV marked “server sendParticles” or “mixed” must keep that separation.
- **Discrete clientbound level effects** belong at the existing `NetworkEvent::LevelEvent` dispatch in `app/core.rs:4444–4490`, not the world sampler. The Java `LevelEventHandler` covers particle-generating event IDs across its `1501–3021` cases (`client/renderer/LevelEventHandler.java:200–590`). Rust currently handles `2001`, `2002`, and `2007` in this branch; the other particle-generating event IDs need comparison and their local spawn requests added there. `BlockEvent` already has a separate dispatch for bell/pot/chest at `core.rs:3830–3858`; add block-event visuals to that event owner only where Java uses that packet.
- **Explosion packet child effects** originate from `ClientExplosionTracker` after explosion metadata is received (`client/multiplayer/ClientExplosionTracker.java:33–52`). Rust has `NetworkEvent::Explosion` handling at `core.rs:3879–3895`, including a primary explosion particle and tracked block effects. Compare this packet-owned algorithm with Java and do not also trigger it from the world sampler.
- **Entity-owned local visuals** belong in entity presentation state/tick, not in a world scanner or generic core branch. `EntityStore` already holds per-entity kind/position/metadata/effect particles and selected timers (`entity/mod.rs:245–288, 313–395, 1382–1450`); movement/metadata/events are delivered through `NetworkEvent` and applied in `core.rs`. However, `in_game.rs` only ticks specific local/player and projectile-display state (`in_game.rs:3630–3680`); there is no full remote vanilla `aiStep`/AI tick. `handler.rs` forwards selected metadata types and discards unsupported serializer types (`net/handler.rs:1485–1847`), so a particle-dependent field may be **wire-received but not semantically retained**. For every entity source, name the needed synced field/event and check the packet decoder, `MetaValue`, and concrete per-kind state before adding anything. Implement the client visual transition from observable state; do not port server AI. Entity event support is selective: `handler.rs:1860` explicitly has TODO for entity event 60 (`makePoofParticles`); inspect its Java call path even though it is outside the 286 `addParticle` search results.
- **Block/item/interaction events** stay with the existing action/event owner in `app/core.rs` / interaction code. For example, potion/block-break LevelEvents already spawn at `core.rs:4444–4489`; other `LevelEventHandler` cases, brush/bucket/dispenser calls, or packet-sent item effects must be assigned by trigger and side. Helpers such as `ParticleUtils` only define sampling geometry; they are not independent emitters. `world/level/Level.java` and `LevelAccessor.java` are API declarations, not generation sites.

## Reference integrity and limitations

`minecraft-26.2-decompiled/README.md` says its official source artifact is the Java **server bundle**. The directory nevertheless contains `src/net/minecraft/client/...` classes including `ParticleResources`, `ParticleEngine`, `ClientLevel` and particle implementations. The exact provenance of those client class files relative to the documented server bundle/decompile process has not been independently verified. Treat them as a useful checked-in reference with this provenance caveat; before final Java-parity signoff, verify the relevant classes against the official 26.2 client jar (or another official matching client artifact). Do not cite the checked-in presence alone as proof of official client-source provenance.
