# Entity / item / client-event particle-source progress

**Status: unfinished.** This file records the implementation completed by the entity/event source worker only; it does not mark the Java 26.2 source inventory complete. Java reference files are under `minecraft-26.2-decompiled/src/net/minecraft` from the workspace root (checked-in client class provenance remains the caveat in `particle-complete-coverage.md`).

## Implemented in this pass

- `Client/pomme-client/src/net/handler.rs::dispatch_world_packet` now maps client-local Java entity-event particle sources to typed events: **0, 1, 3, 6, 7, 12–15, 17, 18, 20, 38, 40–42, 45, 46, 53, 54, 60, 67**. Event 3 preserves its existing death/impact event in addition to the particle signal; 20/60 use the Poof event. Unknown IDs remain ignored.
- `NetworkEvent` adds `EntityParticleEvent` and retains dedicated `EntityPoof`, honey, and drown events. `EntityStore`/local-player position, per-kind dimensions, current/previous positions, velocity, Arrow effect color, equipment stacks and projectile stacks feed the core-side routines.
- `app/core.rs` handles entity effects for rabbit block sprint; snowball/egg impact; taming; villager emotion; witch; breeding (animal/Allay); dolphin; ocelot trust; fox eating; arrow potion color; portal effect; honey-block slide/jump; mob spawn/death Poof; and drowning. Poof uses the entity AABB dimensions (`LivingEntity.makePoofParticles`); Drown uses the Java triangular offset distribution. Firework event 17 now routes the retained Fireworks component, including empty explosion lists, into `FireworkStarterRequest`; Poof fallback is limited to an absent component.
- `app/core.rs::NetworkEvent::LevelEvent` covers Java particle-generating IDs **1500–1505, 2000–2004, 2006, 2008–2013, 3000, 3002–3009, and 3011–3021**. Existing potion **2002/2007** and destroy-block **2001** logic remains intact. **3000** keeps Java's `overrideLimiter=true` and `alwaysShow=true`; ordinary local `addParticle` triggers use both flags false.
- `NetworkEvent::BlockEvent` now retains the packet `BlockKind`. Its client dispatch implements `NoteBlock.triggerEvent`'s `NOTE` particle only when both packet and current state are note blocks and the state instrument is tunable. Inspection of Java `ClientPacketListener.handleBlockEvent -> Level.blockEvent -> BlockState.triggerEvent` plus all block-entity `triggerEvent` implementations found no additional client particle emitters: chest/shulker/pot/bell/spawner callbacks animate or update BE state; the particle-producing trial-spawner/vault presentations arrive as LevelEvents or BE client ticks. This avoids duplicating the BE worker's ticking sources.
- All additions use existing `ParticleStore::add_particles_from_packet` typed spawn/options paths; no local particle engine was added. Server `sendParticles` sources remain packet-owned.

## Not completed / remaining gaps

- **Entity natural/local sources:** the inventory has 53 `entity/projectile client-local visual trigger` rows and 6 mixed local/server rows. This pass did not implement the 53 entity/projectile files' complete local source conditions. Movement/fluid contact, age/baby transitions, breeding, eating, ambient species effects, blaze/witch/warden/dolphin/firework, projectile and indirect helper occurrences still require line-by-line review and client-observable state. Do not infer parity from existing entity animation or effect metadata.
- **Remaining discrete client-event parity gaps:**
  - Entity event **17** now consumes the retained Fireworks component through `FireworkStarterRequest`, including an empty explosion list; the legacy Poof path runs only when the component is absent. The typed starter's in-game lifecycle/render parity remains unverified.
  - Level event **1504** now resolves the first non-pointed-dripstone root above a same-direction stalactite with Java's 10-step search bound, and consults the existing shared `dripstone_attributes_at` query for mud evaporation and `DEFAULT_DRIPSTONE_PARTICLE` fallback. `PointedDripstoneBlock.findRootBlock` uses a contiguous same-block/same-direction path; it does not use the separate `canDripThrough` predicate used by cauldron scans.
  - Level event **1505** uses generated Java block-instance metadata for `BonemealableBlock.Type` and exact `getParticlePos(BlockPos.ZERO)` offsets. `StateDump.java` reflects the interface/type and position method per registered state; decompiled Java has explicit position overrides in `MangroveLeavesBlock` and `RootedDirtBlock`. blockgen compacts the results into `b` (type) and `g` (offset). The table classifies **721 states** (7 neighbor-spreader, 714 grower); those offsets are `(0,-1,0)`. Dispatch applies type-scaled counts, Java spread widths, `Blocks.WATER` fallback, particle-position state/shape height, spreader-only below-air filtering, and the Bone Meal use sound. No Rust block-name list or substring inference remains.
  - Events **2011/2012** use Java-generated `getShape(EmptyBlockGetter, ZERO).max(Y)` metadata (`j`, 1/32 units), including empty-shape `-infinity` and Java air=1.0. Java passes `allowFloatingParticles=true`, so no below-block suppression applies. The shared world/block query uses the existing container animation for dynamic shulker outline height.
  - Event **2013** retains Java's two-ring distribution and signed-count behavior; untrusted count is bounded at 4096 input units. Since Java rounds both loops independently, this permits at most 4097 generated requests; `ParticleStore`'s reservoir is a separate memory limit and does not bound dispatch CPU work.
  - Event **3006** calls shared `world::block::is_collision_shape_full_block(&ChunkStore, pos)` using Java's `isCollisionShapeFullBlock(EmptyBlockGetter, ZERO)` result (`h`), not `blocks_motion` or aggregate bounds. The generated table records **199 dynamic-shape states**; bamboo/speleothem false overrides remain false, shulker collision stays full as its outline animates, and `moving_piston` consults its retained moved-state/progress NBT instead of treating it as a full cube. Stairs with cube-wide aggregate bounds are tested false.
  - Event **3015** emits activation smoke/flame and calls the BE-owned `vault_connection_particles` helper with connected UUIDs/range, facing/keyhole, player UUID, height and position. Java event activation and periodic BE tick are independent helper calls; no `% 20` suppression drops either. A focused test emits an activation burst before the game-time-20 BE tick and another after it, each with the expected 2–5 connected-player paths; the table also verifies no BE is a no-op. Event **3016**'s 20 deactivation flame requests remain.
- LevelEvents **2005** and **3010** have no particle case in Java `LevelEventHandler.handleLevelEvent` (1500–3021); 3001 is sound-only. They are intentionally not assigned fallback particles.
- `core.rs::level_event_builder_outputs_are_table_driven_for_every_typed_particle_case` drives the production pure builder for all listed LevelEvent IDs and checks typed output variants (particle, potion break, destroy block), particle kind/options/count or range, positions/velocities, flags, sound-only/no-op IDs and invalid states. The packet fixture separately checks event ID/data transport. These focused tests have now passed in this checkout.
- **Block-event packet visuals:** NoteBlock was the missing particle trigger. Java BE event callbacks otherwise do not directly emit particles; state animations stay with BE state owners, and discrete LevelEvents are not duplicated.
- **Item triggers:** the inventory marks two item-interaction client trigger rows. They are not implemented here. `ItemPickedUp` already moves/removes the tracked item and plays the pickup sound in `app/core.rs`; it has no particle route. Java's pickup behavior is an item-entity take/model animation, not a fake particle quad. If the existing item renderer lacks that animation, expose an item-renderer take-animation request before claiming pickup parity.
- Metadata not represented as an exact client-visible field remains a dependency for entity-specific sources. Retain only synced presentation data; do not emulate server AI or random ticks. Version-sensitive metadata serializer handling must continue to be audited across supported protocols 1.20–26.3.
- No Java in-game comparison was run, and the original screenshot particle is still unidentified.

## Boundary / non-duplication decisions

`NetworkEvent` decoding owns translating the entity-event byte into semantic visual requests; the core event dispatcher owns spawning the client-local effects; `ParticleStore` remains the owner of particle instances. `LevelParticles` and explosion packets remain authoritative for explicit server particle sends. Entity-local update simulation is not moved into core event dispatch, and the world worker's animate/weather/block/fluid sampler remains separately owned.
