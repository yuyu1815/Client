# Dynamic block API map (read-only investigation)

Scope: `Client/pomme-client`; source inspection only. No source, git, benchmark, build, test, or check commands were run. No helper explicitly named `AssetResolver` exists in `renderer/mod.rs` (search in that file found only `crate::assets::resolve_asset_path_with_packs` usage); the actual public selection API is on `BlockRegistry`. This is the key reason a prior probe can report zero when it looks for a nonexistent “dynamic block helper.”

## State-specific baked model contract

`world/block/registry.rs` owns `pub struct BlockRegistry` (fields private): `baked: HashMap<String, HashMap<String, Vec<WeightedBakedModel>>>` and `multipart: HashMap<String, Vec<MultipartEntry>>`. Renderer owns it; `Renderer::registry(&self) -> &BlockRegistry` at `renderer/mod.rs` makes the getter available without transferring ownership.

Actual APIs:

```rust
registry.get_baked_model_at(state: BlockState, x: i32, y: i32, z: i32) -> Option<BakedModel>
registry.get_multipart_quads_at(state, x, y, z) -> Option<Vec<BakedQuad>>
```

`get_baked_model_at` matches block ID and current state properties against subset variant keys, then chooses weighted alternative using position-seeded `model::model_seed_for_position`; returns a **cloned** model. `get_baked_model(state)` instead returns the first alternative (not position-selected). Multipart checks `WhenCondition::matches(super::block_properties(state))`, chooses weighted entry models with `multipart_seed_for_position`, concatenates quads. It returns no merged `BakedModel`; caller must emit/convert these separately. `get_baked_model_at` does not combine multipart. For reproducible entity geometry, pass a synthetic/fixed position, or use `get_baked_model(state)` only if first-choice semantics are acceptable; don't call the private `get_baked_alternatives` / `choose_baked_model` from outside these modules.

`BakedModel { quads: Vec<BakedQuad>, ambient_occlusion: bool, is_full_cube: bool, occludes: bool }`. `BakedQuad` fields are `positions: [[f32;3];4]` in block-local 0..1 coordinates, `uvs: [[f32;2];4]` (sprite-local, fractional), `texture: String` (resolved texture key, e.g. block texture name), `cullface: Option<Direction>`, `tint_index: Option<i32>`, `tint: Tint`, `item_tint: ItemTint`, `shade_light: f32`, `shade_face: Option<Direction>`, plus `ambient_occlusion`. There is no `normal` field: derive cardinal normal from positions (`direction_from_positions`, `pub(crate)` in model) or use `item_entity.rs`'s private `cardinal_normal`/`pack_normal` during item mesh build. `cullface` is render culling metadata, not necessarily a usable geometric normal.

Variant rotations happen during JSON baking, not an exposed runtime rotate API: `bake_resolved_model_with_item_tints` applies `rotate_positions` around model center for blockstate `rot_x/rot_y`, rotates cullface, and honors `uvlock`; exported baked geometry is already rotated. For entity runtime orientation, use the `ItemRenderInfo.model_matrix` transform path (or held-item draw transform); avoid chunk packed vertices and region origin.

## Existing conversion/upload/draw route

`renderer/pipelines/item_entity.rs` has private `ItemVertex` repr(C): `position [f32;3]`, `tex_coords [f32;2]`, `light_tint u32`, `normal [i8;4]`; Vulkan attrs are locations 0..3, formats `R32G32B32Sfloat`, `R32G32Sfloat`, `R8G8B8A8Unorm`, `R8G8B8A8Snorm`, offsets 0/12/20/24. `build_item_mesh_texture(model, uv_map, vanilla_gui_order, standalone_skin)` (private) already performs precisely the reusable conversion: six vertices per quad (`[0,1,2,2,3,0]`), positions shifted by `-0.5`, model UV remapped through `AtlasRegion.u_min..u_max/v_min..v_max`, item tint/shade packed, normal computed. Existing public `ItemEntityPipeline::ensure_mesh(device, allocator, name, model, uv_map)` calls it then `insert_mesh` -> `util::create_mapped_buffer(... VertexBuffer ...)`. `mesh_handle(name) -> Option<(vk::Buffer,u32)>` exposes uploaded buffer/count; `draw(cmd, frame, items)` binds and submits. `ItemRenderInfo` is the world-drop draw contract: `item_name`, `model_matrix`, `light`, `nether_lighting`, UUID/position/age/spin/bob/count and optional head/dye details. For reuse, building a temporary named mesh via `ensure_mesh` is possible, but it is private-cache-by-name and returns no status; truly per-kind dynamic models need a stable key or a small method to build/upload arbitrary quads without falsely inheriting item semantics.

`held_item.rs` has separate `HeldItemInfo` (`name`, head profile source, `light`, `has_3d_model`, `nether_lighting`); `HeldItemPipeline::update_and_draw` resolves a mesh by `meshes.mesh_handle(name)`, applies held/display matrix, then binds/draws. It does not resolve block state itself. The shared format/mesh builder is in `item_entity.rs`.

`AtlasUVMap::get_region(&str) -> AtlasRegion` provides `u_min/v_min/u_max/v_max`, `pixel_rect`, public `sprite: u16`, alpha flags/counts. `TextureAtlas::build(device, queue, command_pool, allocator, jar_assets_dir, asset_index, texture_names: &HashSet<&str>, generated_item_textures: &HashSet<&str>, packs)` is the atlas registration/build API. `texture_names` must include every face `quad.texture` key before building; keys omitted from the map become missing-tile region (`sprite=0` fallback), not dynamically inserted. No incremental sprite-registration/cache-flush API found. Resource-pack path is `Renderer::reload_assets`: reloads registry, clears item meshes, destroys/rebuilds atlas using `registry.texture_names()` plus generated textures, then `rebind_atlas` on chunk/item/gui/held/particle consumers and re-warms item meshes. Thus dynamic textures require atlas rebuild/rebind, not merely mesh cache invalidation. `Renderer::atlas_uv_map(&self)` exposes current map only.

## Boundaries and minimal edit candidates

- `renderer/mod.rs::warm_item_meshes(device, allocator, item_entity_pipeline, uv_map, registry)` illustrates current call pattern: `registry.get_item_model(name)` then `ensure_mesh(...)`. It is for item definitions, not native block-state geometry. Item JSON icon/flat sprite (`get_item_particle_icon`, flat texture getters) is not equivalent to state-specific block model/multipart quads.
- Renderer-owned registry is accessible through `Renderer::registry() -> &BlockRegistry`. `BlockRegistry`’s maps stay private; use existing public getters.
- Entity model renderer (`entity_model.rs`, `entity_renderer.rs`) bakes `BakedEntityModel` into `Vec<ChunkVertex>` (position + packed terrain UV + light/tint); entity renderer stores model variants per `EntityKind` and texture variants/cache. Active orb/crystal/stand work is entity-core and not needed here. The reusable nearest route for block faces is item pipeline’s float-UV `build_item_mesh_texture`/`ensure_mesh`, not entity model cube construction. `ChunkVertex` uses `tex_coords: [u16;2]` and chunk atlas sprite packing; do not copy it into a rotating entity model or pass chunk region-origin/packed 16-byte assumptions through.
- No existing generalized block-face-to-dynamic-entity helper was found. Lowest-surface-area candidate edits if implementation is later requested: (1) `renderer/pipelines/item_entity.rs` expose a focused quad-to-`ItemVertex` upload entrypoint/reuse `ensure_mesh` for selected baked model; (2) `renderer/mod.rs` provide selected state+position orchestration and ensure its `quad.texture` names are included at atlas build/reload; (3) only if textures are introduced after atlas construction, modify `renderer/chunk/atlas.rs`/`reload_assets` to rebuild atlas and rebind all consumers. Do not edit `registry.rs` unless API must return a combined baked+multiparts `BakedModel`; two actual getters already cover selection.
