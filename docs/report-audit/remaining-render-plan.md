### RENDER-night — strong code-level lighting mismatch, precise source

- `pomme-client/src/renderer/chunk/mesher.rs::world_brightness` uses `LIGHT_TABLE[max(raw skyLight, blockLight)]`; table is `[0.05, 0.067, ..., 0.815, 1.0]`. That terrain vertex path has no day/night sky-darken input. The separate `pomme-client/src/app/phases/in_game.rs::lightmap_brightness` path does subtract `skyDarken = 15 - SKY_LIGHT_LEVEL`; it is used for scalar-lit entities/vignette, not the Java RGB particle LUT. Particle billboards now use `particle_lightmap_settings` plus `evaluate_lightmap_attributes`: the received visual sky-light color/factor timeline is evaluated before weather, then lightning and End flashes, and the result is uploaded in the existing Camera UBO. Thus this terrain finding is not evidence of a remaining particle day/night/weather mismatch. Vanilla biome definitions do not override those lightmap attributes; camera-position biome layers are not implemented because none of the 26.2 vanilla biome definitions use them.
- Remaining code target: correct terrain `world_brightness` where raw skylight is combined with block light; keep it separate from particle lightmap Settings. Do not apply the particle RGB LUT or a night tint to the terrain shader. The particle input path uses registry `visual/sky_light_color` and `visual/sky_light_factor` tracks plus Java weather/flash layers; its focused tests are recorded separately below.
- Validation status: particle lightmap unit tests cover native day timeline at noon/sunrise/night, rain/thunder, lightning override, End-flash intensity, explicit dimension values, registry timeline parsing, and transfer of evaluated frame attributes into `Lightmap::generate`; these focused tests passed (9 tests total). Terrain `world_brightness` still needs a separate daylight/night vertex-light test and the exact RENDER-night capture/trace (18,000; glowstone `(0,64,0)`, torch `(5,64,0)`, camera feet `(0.5,66,10.5)`).

### RENDER-sky-band — clear/dome boundary math can produce a real band; pixel attribution limited

- `SkyPipeline::update_and_draw` sets sky dome to `sky.sky_color_linear()` and `sky.frag` mode 0 paints that constant color. `build_sky_disc` generates top disc at y=16, radius 512. `Renderer` clears framebuffer using `SkyState::clear_color_linear(dimension, render_distance)`; overworld mixes weather-adjusted `FOG_COLOR = (192,216,255)/255` toward the unmodified `SKY_COLOR` using `sky_fog_end=min(32, render_distance_chunks)`, `t=sky_fog_end/32`, mix=`1-(0.25+0.75*t)^0.25`, then converts sRGB to linear. At render distance 10, `t=0.3125` and mix is about `0.166`; thus clear color is about 83.4% fog color while dome is sky color. At render distance 32 or above the mix is zero (clear color is fog color). The clear area beyond finite disc and dome interior are intentionally different inputs, so their boundary can show as a color band where visible. This mismatch is directly present in source math, but absent captured images prevent confirming that it is the particular reported boundary rather than another horizon/fog edge.
- A separate `clear_color_linear` equality/unit test only checks its own Java atmospheric-fog formula; it does not ensure the finite dome edge matches the framebuffer clear value. `sky.frag` itself has no vertical gradient or band-generating shader math; do not tune its shader speculatively.
- Minimal exact next action: capture a camera/horizon frame plus frame trace for clear RGB, dome RGB, render distance, disc clipping, and fog state; compare boundary pixels. If mismatch maps to disc edge, smallest target is `sky.rs`/sky pipeline geometry/render strategy to make clear and dome edge agree under same weather/time (e.g. extend/fade geometry using already-calculated clear/dome colors), not arbitrary shader color constants. If it maps to terrain fog boundary, inspect fog inputs separately. Tests: `SkyState` expected values at distances 10 and 32/weather states and a render screenshot sampling the finite-dome boundary against clear background. No shader edit recommendation before pixel confirmation.
