# Command block / command error investigation (read-only)

対象: Client, batch01/04 command_block / chain_command_block / repeating_command_block と `COMMAND-error-context`。このメモは実装・ビルド・テストを行わない調査結果。別 agent 編集中の core/phases/net/entity/interaction は読んだだけ。

## 結論

- 3種の command block は `MenuKind` のコンテナではない。既存 UseItemOn はサーバーへ送っているが、コマンドブロック応答を編集画面に結びつけるイベント/画面/送信 packet 経路がない。`opens_menu` にも未登録で、既存UI dispatch は command block editor を扱わない。
- Vanilla 26.2 の右クリック認可は server-side `Player.canUseGameMasterBlocks() = abilities.instabuild && permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER)`。`CommandBlock.useWithoutItem` はこの条件で `openCommandBlock`。`ServerPlayer.openCommandBlock` は `ClientboundBlockEntityDataPacket.create(commandBlock, BlockEntity::saveCustomOnly)` を送る。すなわち UseItemOn が要求、コマンド block entity data が認可後応答で、別の OpenScreen/MenuKind ではない。
- Pomme は `BlockEntityData` を受ける generic route まではあるが、それを UI open signal として使っていない。最小案は UseItemOn の対象 block pos を pending にし、同じ pos の command-block `BlockEntityUpdate` が返った時だけ response NBT から editor を開く。応答がないユーザーは開けない。`SetCommandBlock` 送信もこの response を得た編集画面からだけ行う。UI 上の推測権限チェックでサーバー認可を代用しない。
- Integrated server でも creative (`instabuild`) と OP permission は別条件。`game_mode == creative` だけで OP を合成/強制しない。ローカルサーバーが持つ permission をそのまま使い、応答で開閉、最終更新は serverbound packet に対する server validation に任せる。
- `COMMAND-error-context` の報告観測は実行後エラーが一行のみ。ただし静的追跡上 `parse_system_chat` および command error component parsing が click/hover または translatable `with` args/context を落とすバグは確認できない。現実行後エラー表示の証拠は手元に raw packet がなく、動的入力/出力を再確認できていない。既存 local parse usage は独自 Brigadier parse/error-context経路であり、server実行後メッセージとは別。

## Command-block の実codeと未実装箇所

- `pomme-client/src/app/core.rs::container_screen_for_menu` は `MenuKind` を chest等の `ContainerScreen` へ写像し、command block は非対応。command block は `ClientboundOpenScreen` / `MenuKind` ではなく、command BE update が editor open trigger。
- 既存専用編集画面の最小再利用: `pomme-client/src/ui/sign.rs::SignEditState::{new,input,draw}`、`pomme-client/src/ui/text_edit.rs::TextFieldState::{new,set_value,handle,render_info}` / `TextInputEvent` / `KeyMods`、`pomme-client/src/renderer/pipelines/menu_overlay.rs::MenuElement` (`NineSlice`, Text, field drawing via `common::push_field_text`, Button sprites)。画面 event routing の例は `pomme-client/src/app/phases/in_game.rs::build_server_screens`: sign_edit がある場合 keyboard/text events、Done button、Escape を消費して他のscreenに流さない。Sign の `new` は packet BE既存値を初期値にでき、`input`/`draw` が TextInput + render既存実装を使う。Command UI は少なくとも command文字列 TextField、mode (Impulse/Repeat/Chain = protocol enum REDSTONE/AUTO/SEQUENCE)、conditional、automatic、track output controls、Done/Cancel が必要。既存 button描画・hit test/keyboard focus helperを使い、別UI framework不要。

### Vanilla 26.2 authoritative flow / exact packet

Decompiled vanilla reference (`minecraft-26.2-decompiled`, static read only):

1. `CommandBlock.useWithoutItem` calls `player.canUseGameMasterBlocks()`. True -> `player.openCommandBlock(commandBlock)`, false -> PASS. Target command block clicks therefore use ordinary serverbound `use_item_on` request, no client-supplied permission field.
2. `Player.canUseGameMasterBlocks` is exactly `abilities.instabuild && permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER)` (`world/entity/player/Player.java:1750`). Creative mode alone does not establish operator permission.
3. `ServerPlayer.openCommandBlock` sends `ClientboundBlockEntityDataPacket.create(commandBlock, BlockEntity::saveCustomOnly)` (`server/level/ServerPlayer.java:1358`). Pomme already maps incoming native `block_entity_data` through `handler.rs` to `NetworkEvent::BlockEntityUpdate`.
4. BE custom NBT has `Command`, `TrackOutput`, optional `LastOutput`, `UpdateLastExecution` in `BaseCommandBlock.save`; command entity adds `powered`, `conditionMet`, `auto` (`world/level/BaseCommandBlock.java:52`, `CommandBlockEntity.java:75`). Mode derives from command block's current block type/state (the UI may read block ID at pos); `conditional` derives from block state. Initialize UI from command + TrackOutput + automatic + mode + conditional; do not treat output/power fields as editable substitutes.
5. Save with native `ServerboundSetCommandBlockPacket` (`ServerboundSetCommandBlockPacket.java:26-60`): fields/order wire body after packet id: packed BlockPos (signed x26/z26/y12 long), UTF-8 protocol string `command` (VarInt byte length + bytes), enum `CommandBlockEntity.Mode` as enum ordinal VarInt (`SEQUENCE=0`, `AUTO=1`, `REDSTONE=2`), one flags byte (`trackOutput=bit0`, `conditional=bit1`, `automatic=bit2`). Packet name is `set_command_block`; native packet id should be resolved by `PacketTable::native().id(Phase::Game, Direction::Serverbound, "set_command_block")`, not hardcoded. `pomme-protocol/src/data/protocol-26.2.json` already includes `set_command_block`, but Azalea `ServerboundGamePacket` / pomme sender has no typed `ServerboundSetCommandBlock` variant; use existing raw path (`pomme-client/src/net/sender.rs::PacketSender::send_raw`, `Outbound::Raw`, connection framing) and `pomme_protocol::wire::{game_serverbound_id,write_varint}` or add codec there. Encoding enum via `write_enum` equivalent VarInt ordinal; raw packet id + body is what `send_raw` expects (connection still frames/compresses/encrypts).
6. Server handler `ServerGamePacketListenerImpl.handleSetCommandBlock` repeats `canUseGameMasterBlocks()` validation, verifies target entity is actually `CommandBlockEntity`, derives direction from live block state, then applies packet mode/conditional to the block state and command/track output/automatic to the BE. Never bypass this by mutating local world/NBT or by setting local permission. No BE editor save should be sent for a target without an accepted BE response.

### Localized UI and net recommendation

Smallest implementation seam, no new menu kind:

1. In the command-block interaction branch (same `InteractionState::use_item` as UseItemOn), record pending `BlockPos` only for matching block IDs `command_block|chain_command_block|repeating_command_block`; still emit ordinary UseItemOn. Suppress local place/item prediction only in the vanilla-compatible no-item/`useWithoutItem` case. Do not swallow normal held-item use wholesale; Vanilla item-on-first + block fallback semantics matter. Clear/expire pending on mismatch, close, dimension/disconnect, and when response received.
2. In `drain_network_events` on `BlockEntityUpdate`, before generic map update can drop information, require pending pos equality and command-block block kind/id, non-None NBT. Treat that matching response as server's authorization signal, then initialize editor from raw returned NBT + block state and clear pending. Unsolicited updates should update world only, never open UI. A timeout/denial gets no editor; don't infer permission from player game mode. This lets an integrated server's real OP/permission set do its job.
3. Add command editor field to `GameState` and include it in `gui_open`/`wants_text_input`/`input_live` checks in `app/phases/in_game.rs`; mirror sign's `build_server_screens` dispatch for text, keys, mouse buttons, Done/Cancel/Escape, and cursor capture. On Done call a `PacketSender` raw encoder with exact fields; close without client-side BE mutation and wait for server update. Cancel sends nothing.
4. Handle local interaction order carefully: server `CommandBlock.useWithoutItem` may open when empty hand or when held-item interaction passes. Existing `opens_menu` is only local click suppression, not permission logic. Do not classify as `MenuKind`, and don't use a generic server-side “open container” event as trigger.

## COMMAND-error-context static trace

- `pomme-client/src/net/chat.rs::parse_system_chat` reads a NBT `Component` via `read_component`, validates overlay and packet end, then delivers the same component through `send_chat` (or action bar). `read_component` calls `Component::from_nbt_tag`; `send_chat` calls `format_chat_component_spans`. It does not turn a received component into a plain string.
- `pomme-client/src/chat_component.rs::Component::from_nbt_tag/from_value/from_object` recursively parses `translate` + `with`; `parse_argument` supports Component args (compound/list), primitive String/Number/Bool and NBT's `{"": primitive}` list wrapper. `preserve_nbt_interactions` recurses into translatable component args and siblings; `Style::from_object` parses modern `click_event` / `hover_event` and legacy `clickEvent` / `hoverEvent`. NBT preservation reattaches click payload tags and nested show_text hover; numeric translation args restore Java numeric text. `ui/text.rs` formatting resolves inherited style and click/hover events. Therefore there is no concrete code loss found in these paths for a server-provided translated parse error, including nested context args and interaction style.
- Existing `ui/chat.rs::syntax_error_component` / `parse_error_component` builds `command.context.parse_error` around local `SyntaxError` with cursor/UTF-16 position and context (`<--[HERE]`); `net/commands.rs::TreeParse::parse_exception` and client-side usage invoke it. This is local parse/suggestion UI only. Server execution errors come over `system_chat`; don't patch local syntax context to fix a server output loss without new evidence.
- Minimal proposal if a raw packet later proves a specific unsupported shape: add a focused regression fixture through `decode_chat` using actual response component NBT (with click, show_text hover, nested translatable args); fix the failing parser/formatter seam only. Current raw evidence is unavailable, so no change warranted.
