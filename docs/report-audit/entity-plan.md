## 既存コードの流れと使える仕組み

- 受信: `pomme-client/src/net/handler.rs::dispatch_world_packet`
  - `AddEntity`は `NetworkEvent::EntitySpawned { entity_type, position, velocity, yaw/pitch... }` を発行（約1161–1200行）。旧protocolのentity type remapは`net/translate.rs::remap_inbound`、AddEntity packet layoutは`net/azalea_compat.rs`。
  - `SetEntityData` scalar Bool/Int/Byte/Float/Longは`NetworkEvent::EntityData`として生indexのまま渡す（約1492–1512）。typed variantsだけが別dispatchされる。既存Typed variants処理はCow/Chicken/Cat/Wolf、villager data等（約1550–1620）。Pig/Frogなどは未接続。
- 格納: `pomme-client/src/app/core.rs` EntitySpawned分岐（約3249–3278）が`is_living_mob`でliving/vehicleを分岐。`register_nonliving_spawn()`は`set_vehicle_spawn_transform`+`set_vehicle_kind`のみ。
- metadata: 同coreのEntityData分岐（約3683–3725）はprojectile / text display / livingへ順に適用。EntityVariant分岐は`set_variant()`。`EntityStore::apply_entity_data()`はlivingのみ、kind-index型の分岐方式。`normalize_ageable_index()`はprotocol<775のageable subclass indexを1繰り上げ（AgeableMob 26.1追加age-locked field対策）。generic Mob flags byteはindex 15、Ageable baby boolは16、subclass fieldは通常18以降の26.x numbering。
- mob抽出: `pomme-client/src/app/phases/in_game.rs` world render entity extraction (約4729–4810) がliving entityを`EntityRenderInfo`化、`entity_extras()`（約6300–6387）でvariant/layer/stateを埋める。Arrowは`arrow_render_infos()`（約5414）、Snowballは`snowball_render_infos()`（約5895）と分離。
- Mob mesh: `pomme-client/src/renderer/entity_model.rs` はモデル定義/bake。`ModelCube`/`EntityPart`→`bake_model(parts, tex_w, tex_h)`がcube verticesとpart rangesを作り、`BakedEntityModel::compute_part_transforms()`がparent/pose/scaleを適用。通常の`EntityYDown`座標変換、`BlockYUp` convention、baby用root/part scale、named part-based animationsを持つ。モデルfile自動読込はなく、mesh bake関数をRustで実装する設計。Arrow含む既存bake一覧を`grep '^pub fn bake_'`で確認。Pig `bake_pig_model` / `bake_baby_pig_model`等の既存資産はある。
- mob登録/texture: `pomme-client/src/renderer/pipelines/entity_renderer.rs::mob_definitions()`に`MobDef {kind,anim,adult,baby,adult_overlays,baby_overlays}`を列挙。`EntityRenderer::new()`はこのdefinitionをGPU variantへ構築。`expected_variant_count()`は一部poolの個数整合のみ検査。`build_variants()`がモデルvertex bufferを作り、各variantのkeyを`resolve_asset_path(jar_assets_dir, asset_index, key)`で引いてPNGをロードし、候補key順にfallbackする。全候補が失敗時はgeneric fallback texture警告（約2562–2574）。ゆえにpath typo/欠損なら静かに豚姿が出るのでなくfallback textureの問題になり得る。`entity_model.rs`自体はtextureを読まず、texture keyはMobDef側にある。
- texture key形式は既存コードで明示済み: `minecraft:textures/entity/<dir>/<name>.png`（`tex_table!` macro）。例: pig temperate adult `.../pig/pig_temperate.png` (旧 `.../pig/temperate_pig.png` fallback)、baby `.../pig/pig_temperate_baby.png`; Cat `.../cat/cat_{all_black,black,british_shorthair,calico,jellie,persian,ragdoll,red,siamese,tabby,white}[ _baby].png`; Bogged `.../skeleton/bogged.png`, layer `.../skeleton/bogged_overlay.png`. テクスチャ本体はClient/assets/iconのみのため、この調査ではjar asset PNGの有無/画素/pack overrideは未検証。registry `asset_id`はvariant JSON由来で通常 `entity/<mob>/<variant>`、renderer keyには`textures/` prefix+`.png`を付ける。
