## 結論

`EntityKind`を受信できても描画されるわけではない。現在の専用非living描画対象は TextDisplay、item entities、限定的な Arrow/SpectralArrow/Snowball、ItemFrame等に分かれ、一般の vehicle を一括で描画する経路はない。対象は既存 `EntityStore.vehicles` を基礎に、次の renderer families として分けるのが最小で安全。

1. **Boat/Raft**: wood/chest差を持つ1つの boat-family draw。既存item/block model pipelineへ押し込まない。
2. **Minecart**: 1つのcart model+kind別の動的ブロックcontent layer。
3. **Thrown items / projectile**:既存item meshパイプライン再利用可能な物と専用モデル/スプライトに分割。既存 Arrow/Snowball extractorを拡張するが、他種をArrow扱いしない。
4. **Display entities**: TextDisplay実装を参考にしつつ、ItemDisplay/BlockDisplayはそれぞれのpayload用rendererを追加。TextDisplayの解決ロジックを流用しない。
5. **動的ブロック/装飾**: FallingBlock/TNT/EndCrystal/ExperienceOrb/ArmorStand/Mannequin専用stateとdraw。entity mob mapや汎用cube/billboard fallbackには入れない。

## Existing ingress, state and rendering facts

- `net/handler.rs::dispatch_world_packet` `AddEntity` (around 1161) emits `NetworkEvent::EntitySpawned` with type, position, velocity, rotations; the `AddEntity.p.data` is currently only consumed for ItemFrame direction and is otherwise **discarded**. `SetEntityData` (around 1493–1620) has separate handling for ItemFrame, TextDisplay and some living holder variants; generic scalar Byte/Int/Float/Bool/Long forwards raw index. Typed `ItemStack`, `BlockState`, vectors/quaternions, pose, etc. are not automatically persisted.
- `app/core.rs::register_nonliving_spawn` (around 995) calls `EntityStore::set_vehicle_spawn_transform` + `set_vehicle_kind`; `NetworkEvent::EntitySpawned` dispatch (around 3202) classifies via `is_living_mob`, and nonliving enters `vehicles`. Core `EntityData` path (around 3683) calls projectile metadata, TextDisplay metadata and living scalar apply only. `EntityStore::apply_entity_data` early-returns unless id is in `living`.
- `entity/mod.rs::VehicleState` (around 1235) holds kind, position/velocity/look, projectile state, ItemFrame fields, TextDisplay fields, passengers. No boat paddles/damage state, minecart contents, ItemDisplay stack/mode, BlockDisplay state, FallingBlock/TNT block state/fuse, ArmorStand pose/equipment, Mannequin profile/equipment, orb value, EndCrystal beam/bottom state.
- World mob extraction in `app/phases/in_game.rs` builds living `EntityRenderInfo`s from `EntityStore.living`; `arrow_render_infos()` around 5414 handles Arrow/SpectralArrow; `snowball_render_infos()` around 5895 handles only Snowball and reuses dropped-item mesh. `build_item_render_infos()` around 5967 handles dropped `Item` entities and snowballs then item frames. There is no boat/minecart extractor.
- `renderer/mod.rs` world draw owns `EntityRenderer`, `BlockEntityPipeline`, `ItemEntityPipeline`; entity models draw at about 2566; item entities draw afterward. TextDisplay is extracted at ~2700 and uploaded/drawn via `BlockEntityPipeline::draw_text_display` before depth clear. Add special draws into this orchestration, ideally one extraction type per graphics path.
- `renderer/pipelines/item_display.rs::DisplayResolver` is **not** an ItemDisplay-entity renderer. It resolves an item's model JSON parent chain and a requested `display.<static key>` (for held/GUI/fixed item geometry), caches that per item name and returns a local transform. `ItemDisplay` instead needs synchronized item stack + display mode + common Display entity matrix/billboard/interpolation, then an item mesh from `Renderer::item_mesh_info` / `item_entity` atlas pipeline. Resolver may inform the selected item's model-local `display` context only; it cannot supply entity metadata, mesh, frustum extraction, world anchor or Display transform. `BlockDisplay` needs model resolution by synchronized block state and Display transform; it is not a cube texture shortcut.

## Confirmed 26.2 metadata indices (Steel registry reference)

Indices below were generated from `third_party/SteelMC/steel-registry/build_assets/entities.json` `synched_data.layers`, including inherited Entity fields. This repository reference is much more authoritative than assumptions based on older protocol. On wire, item/block/rotations are typed metadata serializers and must be routed as such, not forced through `MetaValue` scalar.

### Common / existing Display path

- Entity common indices: `0 Byte shared_flags`, `1 Int air`, `2 OptionalComponent name`, `3 Bool name-visible`, `4 Bool silent`, `5 Bool no-gravity`, `6 Pose`, `7 Int ticks-frozen`.
- Display common: `8 Int interpolation-start-delta`, `9 Int interpolation-duration`, `10 Int pos/rot-interpolation-duration`, `11 Vector3 translation`, `12 Vector3 scale`, `13 Quaternion left-rotation`, `14 Quaternion right-rotation`, `15 Byte billboard`, `16 Int brightness override`, `17 Float view range`, `18 Float shadow radius`, `19 Float shadow strength`, `20 Float width`, `21 Float height`, `22 Int glow-color override`.
- TextDisplay: `23 Component text`, `24 Int line width`, `25 Int ARGB background`, `26 Byte text opacity`, `27 Byte style flags`. Existing code stores 11–15 as transform and 17/24–27 as fields; handler converts index23 formatted text. (TextDisplay background/styles do not make ItemDisplay semantics.)
- ItemDisplay: `23 ItemStack`, `24 Byte ItemDisplayContext/mode`. Both currently have no corresponding state pathway; index23 is *not* TextDisplay text. Use generated `EntityDataValue::ItemStack` and preserve full stack/components, not `item_name` only.
- BlockDisplay: `23 BlockState`. Must preserve complete block state (including properties) and resolve existing baked block model/material; current path drops it.

### Vehicles

- AbstractBoat/Raft: `8 Int hurt`, `9 Int hurt direction`, `10 Float damage`, `11 Bool left paddle`, `12 Bool right paddle`, `13 Int bubble time`. Spawn kind carries wood/raft/chest variant; store metadata drives paddle animation/hurt rocking. AddEntity data not needed for wood, but ensure packet AddEntity `data` preservation isn't confused with sync indices.
- AbstractMinecart: `8 Int hurt`, `9 Int hurt direction`, `10 Float damage`, `11 OptionalBlockState custom display block`, `12 Int display offset`. Furnace: `13 Bool fuel`; command-block cart: `13 String command name`, `14 Component last output`. Metadata state can style/render cart content; kind selects default chest/command/furnace/hopper/spawner/TNT content. The metadata model does not include TNT fuse for TNT minecart; do not invent one.

### Thrown/projectile entities

All use common 0–7. `trident` inherits AbstractArrow: `8 Byte arrow flags`, `9 Byte pierce level`, `10 Bool in-ground`, `11 Byte loyalty`, `12 Bool foil`; ordinary Arrow also has `11 Int effect color` and SpectralArrow no such field in reference. Current projectile code uses no-gravity index5 and in-ground index10. Thrown item family Egg, EnderPearl, ExperienceBottle, SplashPotion, LingeringPotion, Fireball, SmallFireball carries `8 ItemStack`; render the actual item stack where vanilla does (potion/bottle/egg/pearl), preserving potion components. DragonFireball / WitherSkull / LlamaSpit / ShulkerBullet have no extra synced data; WitherSkull has `8 Bool dangerous`. `fireball` = LargeFireball (has stack field); `small_fireball` also stack field. Keep orientation from current position/velocity/look, use size/texture per projectile kind, not all-billboard.

### Falling/dynamic/decorations

- FallingBlock: metadata `8 BlockPos start_pos`; **block type/state is AddEntity spawn-data (`AddEntity.p.data`)**, not this metadata. Existing `handler.rs` discards that data except ItemFrame. Extend event/state to capture the protocol block-state ID and resolve block model. Also accept block metadata index8 for fall origin/render details.
- Primed TNT: `8 Int fuse`, `9 BlockState block state` (default TNT). Use actual TNT block baked geometry/material and vanilla fuse flash/scale/brightness timing.
- ArmorStand: inherits Living indices 8–14, then `15 Byte client_flags`, `16..21 Rotations` for head, body, left/right arms, left/right legs. Flags select small/arms/baseplate/marker/visibility behavior; equipment comes through SetEquipment packet. Handler currently only emits saddle equipment, so retain all equipment slots for stand draw. Dedicated articulated stand geometry + held armor/items, never mob cuboid.
- Mannequin: inherits Living 8–14; `15 HumanoidArm main_hand`, `16 Byte customization`, `17 ResolvableProfile`, `18 Bool immovable`, `19 OptionalComponent description`. Also must receive SetEquipment for apparel/held items. Geometry/player skin/profile and pose must be distinct mannequin draw behavior; no metadata fields 16+ currently stored for vehicles.
- ExperienceOrb: `8 Int value`; size/value and animated orb texture/rotation require dedicated orb renderer, not dropped Item path.
- EndCrystal: `8 OptionalBlockPos beam target`, `9 Bool show bottom`; draw animated crystal model, optional bedrock base and beam. Not a BlockEntity entry.

Equipment requires extending `handler.rs` SetEquipment path and core event application, retaining `ItemStackData` components.
3. **Boat family draw:** new CPU extraction (best `app/phases/in_game.rs` adjacent to `build_item_render_infos`) produces `BoatRenderInfo { kind/wood, chest, position, yaw, hurt/damage, paddles, bubble/rock state }`. New renderer module `renderer/pipelines/vehicle.rs` (or boat submodule) batches one proper hull mesh per wood material family and a chest mesh for chest-boats; bamboo raft has raft-specific deck geometry. Animate paddles with indices11/12 and rocking with damage; basic static spawn must draw without metadata. Resolve material from correct versioned boat/chest_boat texture path. Draw from `renderer/mod.rs` world pass alongside entities, not `MobDef`.
4. **Minecart family:** same family pipeline, independent cart mesh + wheels; transform/orientation based on interpolated rail/vehicle position and yaw. Add content only via current block renderer/model data: chest block, command block, furnace block (lit state from index13), hopper, spawner, TNT. Custom block from 11 overrides default and offset from12; TNT minecart fuse is not supplied as synced field so don't animate unsupported fuse data. 5. **Projectile family:** generalize extraction rather than MobDef: `arrow_render_infos` can remain its arrow-specific function; introduce separate thrown-projectile extractor for item-model objects and special models. Use `item_entity` baked atlas mesh helper for egg/pearl/potions/bottle when official 26.2 model agrees; pass world rotation and stack item/model components; fired item stack field index8 retained. Trident requires its own held-weapon-like model/texture, not snowball mesh. Fireball/dragon fireball/wither skull/shulker bullet/spit require their distinct vanilla geometry/material and sizes; some may use emissive animated sprites, but test silhouette/orientation and don't make every one billboard. Add lifecycle/collision only where existing `ProjectileDisplay` integration works; at minimum rendering should use authoritative packet transform/velocity.
6. **Item/BlockDisplay:** extend the `EntityStore.vehicles` extractor to make ItemDisplay render record (23 full stack, 24 mode, 11–15 matrix/billboard, 16 light/17 view-range/other visibility fields) and draw the existing baked item mesh through item atlas pipeline. `DisplayResolver` is for resolving item JSON display-context transform; actual ItemDisplay matrix is the world Display transform from metadata and context determines item rendering context. BlockDisplay uses index23 full `BlockState`, resolves block model via `world/block/model.rs`, then translates/scales/rotates with same 11–15 Display transforms and billboard mode. Implement common Display matrix once only if it exactly follows current `text_display::text_matrix` conventions (camera-relative f64, interpolation, billboard, left/right quaternion and scale); don't route its `Component` index23 through text handler.
7. **FallingBlock/TNT:** introduce block-state special extraction using `world/block/model.rs` baked model + chunk/item atlas conventions, not mob renderer or a single cube. For FallingBlock decode spawn-data as state ID then blockstate start position8; TNT uses state9/default TNT block and fuse8 for pulse scale/flash. Correctly set texture/material/transparency and block state properties. For TNT, use the block texture/model rather than guessed entity texture.
8. **Orb, crystal, stand, mannequin:** dedicated meshes/extractors. Orb uses value8 and vanilla animated translucent sprite/tiny quad/rotation; EndCrystal uses `end_crystal` texture and model constants, show_bottom9 and beam target8. ArmorStand is articulated wood stand + metadata rotations16–21, flags15 and equipment. Mannequin is a player/mannequin body using profile17/customization16, immovable18/description19 and equipment packet. Share existing ItemRenderInfo/item mesh only for actual attached equipment; don't call mob fallbacks.
