## 対象と責任境界

この仕事の責務は、packの発見・検証・選択・順序・resource読み取り・metadata解釈・世代切替を一つのclient resource境界で保証すること。消費側が個別にpathを組み立てたり、active pack一覧を独自に再評価したりしない。モデル選択/bake、描画の見た目、glyph shaping、音声再生等のドメイン意味論は各consumer ownerに残し、resourcesが渡すsnapshot/契約とconsumer側reload完了条件を合意する。

**責任分担**

- **Resources / Pack manager:** `ResourceId(namespace,path)`の検証、`PackDescriptor`、selected order、`ResourceGeneration`、namespace index、directory/ZIP読み取り、安全なingestion/cache、metadata/filter/overlay、stack/list API、generation lifetime、reload barrierと共通失敗分類を所有する。正本はこの管理境界に一つだけ置く。
- **Protocol / connection owner:** push/pop識別子とrequest generation、URL/hash/required/prompt、wire packet decode/queue、ACCEPTED/DOWNLOADED/SUCCESS等のwire status・disconnect規則を所有する。resource層へは検証済み候補とrequest identityを渡し、resource層からは適用成否・generation identityを受ける。wire status名やpacket semanticsをresourcesに複製しない。
- **Launcher owner:** vanilla/runtime取得・初期asset供給経路を一本化する。server-pack transport/downloadとlauncher取得を混同しない。初期assetの取得はlauncher担当であり、resource managerはlauncherから渡るasset input/欠損時errorの取り込み境界だけを定義する。
- **UI owner:** local pack選択/並べ替え、確認とcompatibility表示を所有し、managerへselection intentを渡す。active orderをUI内で別に再構成しない。
- **Consumers:** language/font/sound/texture/atlas/model/particle/renderer/mesher/UIは同じgeneration snapshotを消費し、cache invalidation・prepare/applyの完了を宣言する。各ドメインのmerge/bake/draw/音の意味論は各ownerとの契約にする。

**公式機能母集合に含める有限面**は、client `PackType`, pack source/selection/order, directory/ZIP supplier, resource get/stack/list, namespace/path validation, filters, overlays, pack format/features metadata, reload lifecycle, client listeners, client consumers, language/font/model/atlas/texture metadataのsource-defined codecs/variants。**payloadの個別ファイル集合、実際のruntime key全数、server datapackの意味論、動的skin/map/glyph等の実行時生成ID、全外部/library reader、描画・音声の意味論**はこの有限母集合に含めない。個々の有限codecを実装することと、payload資産がすべて揃うことは別の完了条件である。

## 公式の機能母集合

### Pack repositoryと資源の意味

`Minecraft.<init>` (`minecraft-26.2-decompiled/src/net/minecraft/client/Minecraft.java:394-403`)のclient resource repositoryは登録source **3個**: (1) `ClientPackSource`（内蔵 vanilla/bundled等）、(2) `DownloadedPackSource.createRepositorySource()`、(3) `FolderRepositorySource(...CLIENT_RESOURCES...)`。source登録数とsource内の個別pack数は別。`ClientPackSource.createVanillaPack`、built-in `Pack.readMetaAndCreate` / `createBuiltInPackLocation` (`ClientPackSource.java:30-95`)はvanilla required/BOTTOM、bundled optional/TOPを定義し、条件付きdev packsも探索する。`DownloadedPackSource.createRepositorySource` / `loadPacks` (`DownloadedPackSource.java:59-79,230-274`)はserver downloaded packsをrequired/fixed/TOPとして公開し、複数packの順を反転処理する。`FolderRepositorySource.loadPacks` (`FolderRepositorySource.java:43-68,77-125`)はuser directory/ZIPをoptional/TOPで検出する。`PackRepository.reload` / `rebuildSelected` / `setSelected` (`PackRepository.java:35-137`)はsource discovery後に選択ID順を再構築し、required packをdefault位置へ挿入する。`Pack.isFixedPosition` / `getDefaultPosition` (`Pack.java:122-132,162-188`)はfixed packsを越えないdefault位置を決める。したがって**全server packが常にすべてのlocal packより上**という一般則はこのsource登録だけから導けない。

`PackType`は有限2値で、`minecraft-26.2-decompiled/src/net/minecraft/server/packs/PackType.java:6-18`: `CLIENT_RESOURCES` (`assets`) と `SERVER_DATA` (`data`)。本planは前者のclient契約のみを対象とし、data pack codec/実行意味論・world generationはserver ownersへ除外する。directoryはroot `pack.mcmeta`、ZIPはarchive内root metadataを持ち、vanilla ZIP supplierは仮想読み取り（全展開を前提にしない）。namespace/pathの妥当性とsymlink validationは`PathPackResources.getResource`, `validatePath`, `FilePackResources.getResource`, `PackDetector.detectPackResources` (`PathPackResources.java:88-179`, `FilePackResources.java:87-148`, `repository/PackDetector.java:27-57`)を参照する。

Pommeの現行挙動は、local packをUI選択順に`active_packs`へ積み、server pack適用時に末尾へ追加するためlocalよりserverが後方となり、`resolve_asset`は後方優先、未発見時はbuiltinへfallbackする。`resource_stack_paths`はbuiltinを先頭、packsを追加順に並べる。このordered behaviorはPomme固有の観測であって公式のsource/fixed/default selection規則ではない（Rust: `pomme-client/src/resource_pack.rs:73-114,209-224,287-329`; `pomme-client/src/assets.rs:87-166`）。公式の選択順は別契約であり、low→highの一つのstack。`MultiPackResourceManager.java:37-66`が順にpackをnamespace managerへ加え、`FallbackResourceManager.java:61-96,110-180`は後段優先、filter barrierをresource lookup・stack・listingに適用する。公開契約は`get(ResourceId)`, `getStack(ResourceId)`, `list(prefix,predicate)`, `listStacks(...)`, namespace discovery, pack attribution/metadataとする。metadata単体も、assets本体とは独立に同じstack・filter評価を通す。DirectoryとZIP supplier、namespace/path masking、sidecar/metadata mergeは同じResourceId境界で比較対象とする。Pommeの現行directory/ZIP inventory・展開経路は`resource_pack.rs:262-329,484-501`; ZIP sidecar/metadata lookupは`resource_pack.rs:92-114`にあり、ZIP仮想supplierや一般的なdirectory/ZIP同一抽象が存在するとは言わない。

### Metadata・format・codecの有限集合

### Server pack consent・feedback・disconnect契約

公式26.2 `ServerPackManager.pushPack`は`PENDING/ALLOWED/DECLINED` consent状態に従い、承認更新`ACCEPTED`、download済`DOWNLOADED`、適用完了`SUCCESSFULLY_LOADED`、最終失敗`FAILED_DOWNLOAD` / activation failure / declined / discardedを区別する。requiredの意味・最終wire status・disconnectはprotocol/server/UI契約であり、resourcesは候補適用の結果とfailure categoryを返す（Java `ServerPackManager.java:51-90,102-143,187-198,231-265,334-353`; `DownloadedPackSource.java:298-303,355-368`）。URL/hash/required/prompt・push/pop identityはconnection/protocol ownerの入力とする。

Pomme現行ではserver pushをgeneration付きqueueへ積み、`ResourcePackPrompt` UIがserver promptとrequired/optionalを表示し、acceptで`Accepted`を送ってdownloadを開始、declineで`Declined`とrequired時のdisconnect理由を処理する。download thread failureは`FailedDownload`に対応し、成功時はpack適用・live assets reload後に`SuccessfullyLoaded`を送る。一方、apply/reload自体の失敗を独立statusへ変換する経路は確認されず、activation-failure parityは未確認。stale generationは無視し、push/pop/removalやdisconnect時のpending状態処理はcore側にある（Rust `pomme-client/src/app/phases/in_game.rs:260-289,2491-2605,3066-3077`; `pomme-client/src/app/core.rs:1438-1445,4044-4092,7112-7192,7242-7287`; `pomme-client/src/net/connection.rs:1303-1309`）。prompt cancel/close/escapeとrequired/optional結果、download-vs-activation failureの観測同等性は静的該当箇所だけでは確定しないため、UI/protocol比較に残す。Wire status・disconnectはprotocol/UI担当、resource managerは候補適用の成否とgeneration idだけを返し、download successをresource publish successとして扱わない。

### Reload lifecycle / rollback比較境界

Pommeの現行reloadはcandidate snapshotを構築して一括publishする方式ではない。server pack completionで`apply_server_pack`しmanager状態を変更してから、renderer/particle/audio/menu等を逐次reloadし、その後feedbackする（Rust `pomme-client/src/app/core.rs:3940-4017,7242-7287`; `pomme-client/src/app/phases/in_menu.rs:124-129`; renderer結果保持の一部例 `pomme-client/src/renderer/mod.rs:2292-2479`）。reload失敗時にはconsumer単位で前のresourceを保持する箇所があるが、共通旧generation・全consumer atomicity・server/local selection rollbackは確認されていない。これが現状であり、候補構築→全consumer prepare→validation/barrier→single publish→failure時旧generation保持/失敗feedback/server-local状態復帰は本planの提案する受入契約である。

公式26.2では`ReloadableResourceManager.createReload`でselected packs/listenersをreloadし、`Minecraft.rollbackResourcePacks`/`clearResourcePacksOnError`は選択をclearしてrecovery reload/toastを行い、二重失敗時abortに進む。server-pack managerには`DOWNLOAD_FAILED`/`ACTIVATION_FAILED`等の回復状態がある（Java `ReloadableResourceManager.java:49-59`; `Minecraft.java:830-847,1019-1057`; `ServerPackManager.java:340-353`; `DownloadedPackSource.java:259-303`）。提案する旧世代維持は公式のclear/reload recoveryと同一挙動ではなく、比較した上で意図差を記録する。受入条件はprepare失敗で旧client generation保持、候補の失敗feedback、required/optionalのdisconnect等protocol/UI動作、server/local selection stateの整合復帰であり、wire statusやdisconnect policyをresources側で決めない。

## 互換にする設計

実装位置の列挙より先に、成立させる状態・責務・順序・失敗契約を次のように定義する。

1. **唯一の正本:** `ResourceId(namespace,path)`はvalidation済みの識別子。`PackDescriptor(source,id,version range,required/fixed/default order,feature/overlay/filter)`は供給元識別・metadata・選択制約を保持する。管理側が`ResourceGeneration` = immutable ordered low→high stack + namespace indexを構築/所有し、local selection/server proposals/builtinの断片状態から複数consumerが優先順位を推測する形をやめる。`CLIENT_RESOURCES`と`SERVER_DATA`は型/entry pointで分離する。required/fixed/defaultの挿入・source interleaveは公式`PackRepository` selected order algorithmに従い、`server always highest`を仮定しない。
2. **全lookup共通:** get/stack/list/metadata/filter barrier/overlayは同一generationと同一stack precedenceで評価する。consumerから直接filesystem path bypassをなくし、snapshot APIを通す。payload byteはgeneration所有で、consumerが参照する間はgeneration refcount/snapshot leaseで生存し、publish後も古いGPU upload等が完了するまでclose/deleteしない。official 13 atlas IDと5 source codecのresource semanticsを満たす実装表現を選び、13 GPU atlasを強制しない。audio/font/model/mesh/render等は自領域のmerge/bake/draw/reload意味論をowner契約として明記する。
3. **世代切替状態機械:** `selection/request → candidate ResourceGeneration → metadata/security validation → dependency DAGに沿うfallible consumer prepare → generation-tagged CandidateConsumerBundle → readiness barrier → single-point publish → server APPLIED/SUCCESS feedback`。resources coordinatorは、candidate resource snapshotに対応する消費側の生成済みhandle/snapshotも束ねた非公開`CandidateConsumerBundle`を所有する。CPU側のlanguage maps、fonts、models、audio definitions等とGPU側資産を含め、schema/codec/provider/decode/GPU allocation/worker waitを含むfallible準備はすべて候補内で完了させる。prepare DAGの依存先および全required upload/worker generation barrierからのackが揃うまで、どのconsumerも既存active stateを変更しない。

   publishではcoordinatorの単一制御点がimmutable `ActiveBundle { resource_generation, consumer_snapshots }`を非fallibleに切り替える。consumerごとにactive pointerを逐次更新して、後続が失敗したら部分適用になる方式は禁止する。frame/mesh/UI/audio readは同一`ActiveBundle` snapshotを取得し、generation identity不一致のreader/job/resultは拒否する。旧bundle/generationは参照中のlease/handleが尽きるまで保持する。既に進行中のsoundのlifetime/停止意味論はaudio ownerとの契約として定め、公開前後に即stopすると仮定しない。stale download/push/popはrequest IDとgeneration IDで除外する。required/server selection responseはfailure categoryとcandidate identityをprotocol/menu ownerへ渡し、wire status/disconnect policyはprotocol ownerが決める。
4. **準備失敗・publish契約・回復:** validation、codec/provider/decode、GPU allocation、worker waitを含むprepareのどの段階の失敗もcandidate全体を棄却し、active bundleを一切変更しない。publishは非fallible swapだけとし、fallible I/O・allocation・consumer個別applyを持ち込まない。既存のexternal/in-place operationを非公開candidateとして準備できない場合は本設計に適合しない未解決事項であり、consumer adapterが完成するまで公開してはならない。required/server selection responseの失敗分類はprotocol/menus ownerへ返すが、retry/disconnect等のwire/UI意味はresourcesで決めない。

   publishの非fallible前提がdevice loss等で崩れた場合はfail closed: frame/command発行を止め、success ackを送らず、generation破損bundleを公開せず、recoveryまたはshutdownへ遷移する。ここに通常の部分apply rollbackは置かない。公式Minecraftのreload recovery/retry/toast/abortと同等かは未知であり、固定版sourceとobservable outcomeを厳密比較して意図差を記録する。Vanilla `ReloadableResourceManager.createReload`は現行managerをcloseして新manager/listenersへreloadし、`Minecraft.rollbackResourcePacks` / `clearResourcePacksOnError` / `reloadResourcePacks`は選択packをclearしてreload/toast、recovery失敗をabortする経路を持つ（`ReloadableResourceManager.java:49-59`, `Minecraft.java:830-847,1019-1057`）。この計画のcandidate保持・atomic bundle publishはPommeの設計であり、公式挙動の一致を前提にしない。
5. **Language/font:** `en_us`/`ja_jp`固定`OnceLock`をnamespace + selected generation's pack metadata discovery + official selected/default language fallbackへ移行し、generation publishで再構築する。5 glyph provider codec全部（`bitmap`,`ttf`,`space`,`unihex`,`reference`）を維持/完成し、provider-local loader errorは他providerを失わせず、reference graphの欠落/循環とfilter/options（`uniform`,`jp`）を扱う。formatに依存しない malformed resource failure分類をresources側で定義し、具体font provider error適用はfont owner契約にする。
6. **Source ingestion/security:** directory/ZIPは同じResourceId/Pack APIへ安全に供給する。Vanillaのsource検証根拠（format/metadata/symlink/detector behavior/cache policy）とPommeで必要なsecurity要件を区別する。ZIP bomb/entry数/展開サイズ/CPU、symlink-follow race、path collision、disk full、中断cache、hash照合は別途脅威要件でboundし、制限値を根拠なしに公式値と称さない。launcher downloadsはlauncher ownerへ一本化。server packではtransport ownerがrequest/feedbackを運び、resource sideはbytes→hash/metadata/security validation→cache→candidate generationを提供し、`ACCEPTED`は同意応答、`DOWNLOADED`はtransfer完了、`SUCCESSFULLY_LOADED`はcandidate適用成功と区別し、resource generation/consumer readiness barrierを満たすまで成功結果を返さない。required failure後のdisconnect/UI表示はprotocol/UI ownerに委譲する。

**実装境界への対応:** resource manager/repository/generation/validation/resolutionを`resource_pack.rs`責務から統合し、`assets.rs`の4 resolver API利用側をsnapshot APIへ順次移す。request identity/wire stateはprotocol/core側、selection intentはUI側、consumer prepare/applyは各renderer/audio/lang/font ownerが実装・登録する。これらは責務対応であり、具体module/API名やGPU atlas個数は後続implementationで選べる。既存pathがあることを理由にconsumerごとにfilter/order/reload補正を追加しない。
