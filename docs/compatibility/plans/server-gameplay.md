### Ownership map

| 契約 / state | owner | 他境界との関係 |
|---|---|---|
| packet decode, transport, ordering key | protocol + PacketProcessor | payloadはintent。decode成功はaction承認ではない。schedule classごとの順序/重複規則を保持。 |
| movement physics | physics owner | clientは予測。server-worldのcollision/block stateとinteraction rangeを参照し、server結果でreconcile。 |
| interaction intent | interaction/game-mode owner | range/hand/sequence/cooldownを検証し、block/item/entity action ownerへ一度だけ渡す。 |
| inventory / ItemStack | inventory/player owner | component/default/removed-patchを保持。consume/durability/remainder/resultをtransaction単位でcommitし、menu/packetは投影。 |
| block + neighbor/scheduled effects | server-world/block behavior owner | gameplayはitem/block intentを決めるが、world block mutation・neighbor update・scheduled effect・broadcastはserver-worldへ委譲。返却されたcommit resultで消費を連動。二重dispatch禁止。 |
| entity lifecycle/transform | world entity manager + concrete entity owner | create/load/spawn/tick/remove/passenger/tracker/saveのmembershipを一元化。entity固有stateはconcrete entity owner。 |
| combat/damage | living damage transaction owner | source attributionを保持し、armor/effects/health/knockback/death/loot/XP/progressionを一つの順序付き結果として発行。 |
| recipe definitions vs execution | registry owns immutable definitions; menu/machine owns input/result | recipe book/progressionはplayer owner。result take時に再matchし、消費・remainders・overflowをatomicに更新。 |
| loot definitions/evaluation | registry/data + caller-owned context/RNG | callerはworld/entity/player provenanceを明示。公式RandomSource/sequenceを呼出境界からnested table/functionへ伝搬。 |
| commands | shared registry/parser + domain state owners | permission/tree projectionと実行時permissionを一致させ、gameplayは同じowner APIへ委譲。 |
| effects | living-entity owner + effect registry/behavior | active instance・duration/amplifier/hidden chain/flags・tick・attributes・persistenceを所有。packet projectionとpresentation eventは分ける。 |
| criteria/progression | per-player progression owner | authoritative post-commit eventを一箇所でdispatchし、progress/rewards/save/client deltaを管理。 |
| particles/audio/HUD | owning simulation event + presentation client | server由来event/packet欠落は比較対象。Pomme client-local rendering/particle/audioは提示層であり未対応だけではserver simulation欠落ではない。 |
| lifecycle | player/world/entity lifecycle owner | join/load/death/respawn/dimension change/unload/saveのsequenceと失敗契約を持つ。 |

## 互換にする設計

1. **Server authority, predictable client:** all mutation outcomes originate from the server state owner. Client keeps prediction keyed to request/sequence and authoritative result version; accepted state replaces/reconciles prediction, rejected state restores from authoritative snapshot. Protocol decode does not mutate gameplay state.
2. **Commit boundary and failures:** ingress/immutable-validation rejection and owner-side stale/conflict rejection do not apply action gameplay mutation; a valid attempt with no damage/no result may still retain official pre-result effects (e.g. attack ticker) and must be compared as such. Commit-before-validation is forbidden. Atomicity is limited to the explicit in-memory bundle; packet send/retry and durable save are separate boundaries. No universal inverse rollback, compensation, or cross-I/O transaction is assumed; publication retry never reapplies action.
3. **Source-derived deterministic tick contract:** extract exact official phase order and compare current Steel tick graph. Preserve per-owner order/cadence, entity snapshot membership and passenger semantics. Only parallelize independent immutable read/plan segments; commit by owner in deterministic order. Do not parallel tick AI/goals/world writes by default.
4. **Entity behavior as dimensions:** use complete ID inventory and separate factory/direct producer/tick/behavior/persistence/tracking/loot dimensions. Factor AI templates only for same rules, retain per-type exception state. Never turn 21/137 into coverage percent or assume generic trait tick supplies mob AI.
5. **Combat, effects and item boundaries:** health/damage/effects/knockback/death/loot/XP and ItemStack consume/remainders are ordered by their state owners with explicit cross-owner commit and observable-event projection. Effects form an independent domain (registry, instance update, tick, attributes, persistence, packet projection). Valid no-damage side effects are distinct from rejection. Resolve crit/sweep/sound and item components from official source/Steel path before implementation.
6. **Typed recipe/loot boundary:** immutable data is distinct from executable consumers. Match and result-taking are separate; loot RNG/context and failure classification originate at caller, flow intact through nested evaluator, and output/drop insertion commits once.
7. **Commands and progression are adapters/consumers:** same mutation APIs as packets/gameplay. Commands differ only by actor/context/permission and user-facing result. Advancement/recipebook/stat events consume post-commit domain events and own durable progress; no scattered per-feature unlock booleans.
8. **Version and denominator discipline:** freeze source/data hashes and registration sets before calculating completion. `unknown` remains a real status. Overall compatibility rate is prohibited until unknown data provenance/mother sets and behavior/state/failure transitions are resolved.
