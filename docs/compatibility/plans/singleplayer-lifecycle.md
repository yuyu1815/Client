## 対象と責任境界

対象はsingleplayerのworld選択・作成・管理からsession開始、権威serverの実行、pause/autosave/leave/failure、保存と資源解放まで。公式Realm upload入口も操作母集合には含むが、hosting/auth/upload serviceは本ownerの実装対象ではなく別owner契約として記録する。Steelにはregion/chunk、level、player、scoreboard/command dataの永続化と順序付きgraceful shutdownがある。「保存がない」とは扱わず、カテゴリ・要求/完了段階・失敗枝ごとに比較する。

- **world lifecycle owner（本計画の主責務）**: worldselection固有操作、正式な`WorldIdentity`/`WorldMetadata`/`StorageCapability`、session state machine、lock、startup rollback、save request/barrier orchestration、stop/recovery選択を所有する。serializerごとの結果を集約し、session寿命と成功/失敗UIを決める。
- **menus**: generic画面/widget/navigation/ユーザー選択値を所有する。保存状態機械・world data authority・server停止順序は持たない。
- **resources**: pack発見・読込・reload・解放を所有する。lifecycle ownerはload/cleanup結果契約を持つ。
- **server-world**: world内容、generation authority、chunk/region意味・永続化形式、DataFixer以外のSteel migrationを所有する。
- **server-gameplay**: authority/player state、player保存内容、command-owned dataの意味とserializerを所有する。
- **protocol**: transport、login/join/disconnect境界を所有する。lifecycleは接続遷移と協調するがcodecを所有しない。
- **connection-and-protocol / cross-feature契約**: Realm uploadのauth、hosting/service、network操作はこのsingleplayer-lifecycleが実装する機能ではない。既存のconnection-and-protocol ownerを窓口として契約先を割当てる。単なる「非対応/なし」として母集合から消さず、横断owner未割当なら`unassigned contract`として未完了に残す。
- **format境界**: canonical identity/metadata/capabilityをPomme sidecar都合から分離し、vanilla `.dat`/`.mca`とSteel `.toml`/`.srg`を同一形式と偽らない。明示的にサポートするconversionだけ形式別adapterで扱い、元形式を保持して検証/変換/rollbackする。自動破壊的上書きは禁止。
- `WorldMetadata`のsidecarは一覧表示・入力候補の所有者であり、既存worldのcanonical authorityではない。Steelでは既存`level.toml`がseedとgeneration metadataの根拠であり、launch seed/generatorとの不一致は検査・拒否される (`steel-core/src/level_data/mod.rs:328-333,408-461`; `steel-core/src/server/mod.rs:569-674`)。

## 比較flowと状態所有

- **A — Pomme → official remote server**: title/server list → connect/login → joined → leave/disconnect。Aの適用範囲はprotocol上のjoin/leave/disconnect境界に限る。world CRUD、local storage、save-format、Realm/hosting uploadはAの比較対象ではない。
- **B — Pomme protocol client → Steel integrated authority**: world-selection metadata → selected path/session lock → Steel level/world authority → Tokio memory protocol pipes → client joined → pause/save/stop → release。Bが本計画のlocal lifecycle主比較である。
- 概略flow（source-observed startup orderingとtargetを区別）: `WorldList(sidecar scan) → selected summary/path → SessionLock → LaunchOptions → Steel server/world load + spawn preparation → server run task + protocol packet tasks start → started notification / Progress::Ready → client join → gameplay-ready (target event; not proven by Progress::Ready) → Running → pause/save requests → cancel/stop → task drain → save_and_shutdown → thread completion → lock release`。source上の両packet task開始は`Progress::Ready`通知より前。各矢印では現在の実装事実と目標契約を区別し、UI遷移やthread完了だけで保存成功としない。
- **所有マップ**: sidecar (`pomme_level.json`) はdisplay name/last_played/UI候補設定。Steel `level.toml` owns persisted seed/generation/world settings: an existing persisted seed is authoritative and requested launch seed does not overwrite it; mismatched saved generation metadata is rejected. Server gameplay owns runtime authority/player/world mutation. Pomme menu/game pause flags own client overlay/input/tick gating only; they are not Steel authority pause. `LaunchOptions` owns only explicitly passed seed/view+simulation distance/game mode/difficulty/allow_commands/storage path/transport; Steel runtime config owns local max-player/offline/no-encryption/no-secure-chat policy; command permission group owns actual command access. Lifecycle owns session lock, readiness/result state and operation ordering (target, not yet fully implemented).
- **Memory transport**: `pomme-client/src/net/conn.rs:282-310` uses two Tokio `SimplexStream` one-way pipes, 256 KiB client→server and 1 MiB server→client. Packet reader/writer tasks carry protocol traffic over these in-process pipes; this is not TCP and does not by itself prove all gameplay readiness.

## Version、recovery、storage safety distinctions

- Vanilla branches remain distinct: unreadable/malformed NBT → recover retry/cancel (plus OOM crash-report branch); version incompatible → block/alert; backup-status confirmation can precede upgrade; DataFixer/file-fixer may run with progress, cancellation/failure; world-stem/pack failures have their own safe-mode/retry paths (`WorldOpenFlows.java:313-435,475-610`). These are not one generic “mismatch”.
- Steel region header/format mismatch is Steel-native: current source renames the old region to versioned `.bak`, then creates an empty current-format region (`steel-core/src/chunk_saver/region_manager.rs:96-143`). That `.bak` is evidence of byte retention in this branch, not proof of a validated backup, DataFixer conversion, or successful recovery. Do not write that no original exists; preserve and inspect exact original/backup relation before any action. It is separate from malformed `level.toml`, corrupt chunk payload/table, and foreign vanilla format.
- **Unknown vs static**: static source proves the described Steel mismatch branch can lead to an empty current region after moving the old file. Whether the end-user consequently sees an empty world, whether unrelated chunks survive, whether UI warns, and whether other source paths restore data are runtime/global-search questions and remain unknown. Do not label “silent empty world” as established runtime fact.
- M0 policy: preserve existing bytes; do not silently create an empty replacement on an incompatible/unknown source or classify it as new-world success. Block unsafe open and offer explicit read-only diagnosis, verified backup/recovery, retry, or cancel. Behavior must be format-specific; official DataFixer handling is not the Steel migration contract.
- **Required safety contract (not current delete behavior)**: identity/path boundary must validate canonical root, traversal/symlink/path replacement, active lock, and overlapping backup/delete/import destination. Active session lock spans server mutation and cleanup. Destructive operations require no live session and verified target ownership; current `remove_dir_all` path does not itself establish these guards.
- Capability reports actual known request/queue/flush/replace/sync behavior and marks unverified guarantees unknown. Do not equate `flush()` or rename with durable media.

## Session lifecycle, failure liveness, and UI result

Target state path (not a claim about current completed semantics): `Closed → Locked → Validating → LoadingPacks → Starting → Joining/Ready → Running ↔ Paused → Stopping → SaveRequested → QueueDraining → PhysicalFlush/owner close → Cleanup → Closed(success or failed/recovery-required)`.

- One session owner coordinates lock, resources, server, connection and stop idempotence. Startup acquires validated lock → metadata → packs/resources → server → transport/join. Failure/cancel unwinds acquired resources in reverse order; success UI/last-played only follows the defined ready/join event.
- Pause UI and authority pause are separate. The official pause transition requests save-all; no equivalent Steel pause/save request is verified here. Compare client-only pause separately, and include both client-paused and empty-player official IntegratedServer transitions; exact multiplayer/LAN conditions require source evidence.
- On stop, stop connection/packet producers, stop authority work, request category saves, perform required pending-work drain and each owner’s supported flush/close, then release session lock. Each stage produces a result; safe later cleanup continues after category failure without converting failure to success.
- **Proposed owner contract, not current behavior**: any save/flush/close failure must remain a structured failed outcome rather than `Closed(success)`, retaining category/phase/cause and completed/failed/unknown peers. UI must not show saved/success. While server may still mutate, prohibit restart/open/delete/rename/backup mutation and lock release.
- Do not promise that named `ErrorHold` / Retry / Backup / Abort UX exists or that Retry works after server stop. Define these semantics in M4 only after lifecycle/server/storage owners specify whether retry uses a live owner or safe reopen/recovery, how source bytes are preserved, and what explicit abort can safely release. A stopped server cannot be retried as though the old authority remains alive. Lock release is permitted only once mutation stopped and cleanup is complete; retry-after-stop remains an open design question until that definition exists.
- User-visible completion has distinct **success** and **failure/recovery-required** outcomes. A successful “saved/closed” indication requires all required categories and close steps to report success under the chosen contract; an incomplete/unknown commit is not represented as success.

## Pause, autosave, and lifecycle save contract

- Verified official contract: on the relevant IntegratedServer pause transition, `saveEverything(false,false,false)` is invoked after the source-confirmed condition/order. This verifies a save-all request/scheduling behavior only, not queue drain or durable commit. Steel pause/save invocation remains unverified; client tick freeze alone is not parity.
- Additional design requirement (not asserted vanilla parity): lifecycle may await category queue drain/flush before showing a completed pause checkpoint. Label this added completion guarantee separately, and keep pending/unknown categories visible.
- Autosave, pause-save, and final shutdown share a scheduler/barrier to avoid concurrent writes; queueing and shutdown final-save behavior are explicit. Do not infer autosave interval from Steel command-data 300s. Official global cadence/timeout remains `unknown` unless call sites establish it.
- During shutdown, source-confirmed official ordering only: packet processing/connection stop, player save, pending chunk work drain, forced world save/flush, resource/storage close and lock release (`MinecraftServer.java:641-690`). Implementation may require further owner-specific phases; do not assert equivalence beyond source evidence.

## Evidence, 100% denominator, and unresolved items

- Do not use a synthetic `all O1–O16 × all seven categories × all branches × A/B` denominator. Build explicit rows from the official operation/branch inventory, classifying each as `applicable` or `not applicable (reason)` with environment A or B, owner/data category, and evidence state. A is only Pomme→official remote-server join/leave/disconnect; B is local Pomme protocol client→Steel authority lifecycle. World CRUD/storage cannot be made applicable to A by cartesian product.
- Cell schema: `(operation ID, exact source branch, applicable data/owner category or external contract, A/B/N/A reason, responsible owner) → source/runtime evidence and gap`. Status is `source verified` / `runtime compared` / `pending runtime` / `unsupported explicit` / `unknown` / `not run`. Keep applicable/N/A reason and source reference on each row; unexecuted checks remain pending, and unallocated owners remain unknown.
- Applicability inventory enumerates O1–O16 and named branches individually: O1 sidecar list vs official candidate/summary/recovery states (B); O2/O5 create/recreate settings/generation and pack/resource result (B); O3/O11 metadata, lock, version, fixer, pack, low-disk, symlink and recovery branches (B); O4 sidecar name/icon/folder (B); O6–O8 delete/backup/optimize and affected storage/serializer owners (B); O9 local import/export not found in bounded official screen group, retained as explicit not-in-scope/N/A with reason and distinguished from conversion (B); O10 official upload selector and external auth/hosting contract, A/B execution N/A but owner contract required; O12 start/ready/join (A only remote join boundary; B integrated start); O13 client pause vs authority/no-player pause and save request (B); O14–O16 only categories and cleanup owners touched by each actual save/stop/failure branch (B, plus applicable A disconnect boundary). Named O11 and O13 branches are separate rows, never rolled into generic “open failed” or “pause”.
- Seven category labels in “保存カテゴリ” are candidate dimensions, not an automatic multiplier: level/settings/worldgen; dimensions/chunks/regions/entities/tickets; players/inventory/stats/global metadata; scoreboard/command data; rules/datapack/registry; bundled resources; UI list record. Assign a category only when the operation/branch touches it; otherwise mark N/A and explain. Exact expanded row count remains **not computed** until M0 inventory emits unique applicable and N/A rows. Unknown/unallocated rows can never silently count as complete. Future 100% means all applicable rows have required evidence and all N/A rows are justified, not a current compatibility percentage.
- Full source coverage is bounded by the explicitly named source roots/classes/callbacks above, including upload mode, WorldOpenFlows OOM and recovery/version/datafix branches, IntegratedServer client-paused and empty-player transitions, and server save/stop. This does not imply hidden third-party integrations were disproven.
- Static source reads establish call sites and API use, not runtime parity. Dynamic cases are currently all **not run**.
