## 対象と責任境界

このplanが扱うのは、clientが受信したBE snapshot/updateとblock state/eventを表示可能な状態へ投影し、world geometry・追加描画・副作用consumerへ渡す契約である。以下の「現状」は確認したsource経路、「提案」は互換化の設計、「未確認」はsource consumer監査待ちとして区別する。

- **状態所有 (提案):** world owner/main threadがpositionごとの受信raw NBT、type/blockstateと、client-only simulation stateの更新・破棄を担う。immutableなNBT-derived render projectionは受理済みsnapshot/updateから導出する読み取りviewとし、client tick/eventで変化するruntime stateとは寿命・ownerを分ける。公式 `BlockEntity` load/updateと各 `getUpdateTag` / `getUpdatePacket` / packet producerを型別に照合するまでは、NBT全replaceかfield mergeかを固定しない。現状の `StoredBlockEntity::update_nbt` はNBT-derived fieldsを再計算しつつ一部runtime stateを保持する（例: conduitは `target_uuid` のみ更新し `tick_count` / `effect_blocks` を残す。`Client/pomme-client/src/world/block_entity.rs:394-411`; particle tick owner `Client/pomme-client/src/world/block_entity_particle.rs:140-185,382-465`）。同型NBT更新でこれらtransient stateを再初期化しない契約を守る。型不正・未知NBT時のraw保持とprojection fallbackは、公式挙動の確認後にfield単位で定義し、以前の異型projectionを流用しない。
- **順序と寿命 (条件付き設計):** まず実際の受信→capture/decode→world apply経路で順序逆転、world/connectionを跨ぐ遅延apply、または古いasync結果の具体的適用経路があるかを調査する。確認した現行pathではchunk decodeはnetwork handler内で `spawn_blocking(...).await` され、その後 `send_event(...).await` で渡されるため、この区間に非同期parallel decodeが適用順を逆転する証拠はない (`Client/pomme-client/src/net/handler.rs:482-545`)。受信イベント後のworld dispatchもmain loopのcaseとして処理される (`Client/pomme-client/src/app/core.rs:5139-5156`)。したがってconnection-generation/receive-sequence/local chunk-generationはPhase 1の前提・無条件要件にしない。具体的なstale apply raceが別経路で確認された場合だけ、そのraceを閉じる最小のowner-side guardを設計する。wire packetにchunk epochがないため、local tokenだけで「同一接続内の遅延した旧server由来packet」を識別できるとは主張しない。

  wire BE update / block update / block event packetにはchunk generationがない。現行Clientはchunk snapshot受理時に対象columnのBE mapとanimation entriesをclearしてから再登録し (`Client/pomme-client/src/app/core.rs:2261-2283`)、BE updateはloaded chunk内の既存同型entryだけを更新し、missing/type mismatchは適用しない (`:2303-2319,5139-5156`)。公式BE updateもpos/type一致の既存BEにだけloadし、不在/type mismatchは無処理 (`minecraft-26.2-decompiled/src/net/minecraft/client/multiplayer/ClientPacketListener.java:1433-1462` `handleBlockEntityData`)。公式block eventは `ClientLevel.blockEvent` に委譲 (`:1478-1481`); chunk不在時動作やreplace/unloadとの順序はconsumer/source comparison待ち。NBT全replace/mergeも各型の公式load/update semanticsを調べるまで固定しない。
- **状態と描画:** server-authoritative NBT/state/blockevent、client-owned tick/event runtime state、render-only interpolationを分ける。rendererはauthorityを作らず、公式26.2のclient render-state extractionとdelegateから入力・式を照合する。pause、partial tick、clock basis、距離/LOD/frustum/light/occlusionはsource comparisonし、未確認のduration/角度/係数を仮定で契約化しない。
- **geometry owner:** 各visible componentに `terrain/blockstate` / `generic BE model` / `special BE pass` / `item-rendered component` のownerを割り当て、同じcomponentの二重描画・無描画を確認する。terrainは通常blockstate/meshを所有し、BEは追加componentを担当する。Sign board/postはterrain、front/back glyphは別BE text pass。item likenessはitem rendererへ委譲する。consumerを未監査のcomponentはownerを仮決めせず、欠落とも断定しない。
- **境界:** resourcesはload/reload・model/material/texture/font/profile resource、block-renderingはterrain/blockstate geometry/light, item-renderingはinventory/hand/item geometry、particles/audioはstandalone effects/output、connection/protocolはtransport、inventory/container/interactionはmenu・編集要求とserver requestを担当する。BE projectionは必要なread-only inputsを使うが責務を吸収しない。SteelMC生成/保存/権威更新と公式server側との差はserver-world/gameplay/lifecycle planへ引き渡す。

## 互換にする設計

1. **固定inventoryを二軸で管理:** 公式26.2 `BlockEntityTypes`の49登録と各`validBlocks`、専用renderer登録26件、非登録23型を別々に列挙する。各型のconsumerは専用renderer有無と独立にterrain/state, item, UI, particle/audio/light, gameplay/eventへ分類する。49型/26登録はcode registryの分母だけで、全validBlock/state/resource variantの閉鎖を意味しない。
2. **Ownerが寿命を管理:** world ownerは受信snapshotとtype/blockstateを更新し、NBT-derived immutable projectionとclient-only tick/event runtime stateを別の寿命として維持する。同型NBT updateはderived projectionだけ更新し、runtime stateは公式のload/update/event contractがresetを要求する場合を除き継続する。Conduitは現行例として`target_uuid`のみ同期し`tick_count/effect_blocks`を保持する。異型交換・column snapshot replacement・chunk unload・world/connection reset時は所有するstate storeごとに失効させ、partial cleanupを残さない。
3. **Guardはrace証拠に従う:** まず受信、非同期capture/decode、event enqueue、world apply、render job completionの具体順とstale適用経路を記録する。現在確認したhandlerはchunk decodeをawait後にevent送信しており、そのpathだけではasync reorderの根拠はない。別経路で順序逆転またはstale applyが確認された場合に限って、world ownerの必要最小のgeneration/token/ordering ruleを決める。tokenはwireにないserver epochを識別できない。
4. **Component単位のdraw/delegate ownership:** terrain/blockstate vs generic BE model vs special text/shader vs item pipelineでvisible componentごとにownerを割り当てる。Sign board/postはterrain、front/back textは別BE pass。Banner generic tintとpattern texture composition、Conduit model/UUID vs particle / item-special shell vs active cage/wind/eye、Beacon beam vs menu/UIは別軸で監査する。texture synthesis・item/resource/particle/state consumerを検索するまでconsumer不明を「missing」と呼ばない。
5. **公式数値を採取して比較:** renderer `extractRenderState` / `submit`と関連 terrain/item/particle/light delegateの実式・clock・partial tick・event duration・distance/culling・light/occlusionをsymbol/path/line付きで記録し、Client値とcaseごと比較する。未調査値は未知のまま。rich text/style/font、resource reload/texture variant、UUID/entity resolution、malformed NBT・unknown typeのfailure policyも対応consumer ownerで決める。
6. **証拠と不確実性を保つ:** official source registration/consumerと現行production sourceの両方を参照し、確認path・検索範囲・結果を明記する。source treeにないasset dataや未調査consumerについて互換差分を捏造せず、「未確認・consumer監査待ち」と残す。動的comparison未実施は達成扱いしない。

## 完了条件と比較ケース

**分母固定:** 26.2 `BlockEntityTypes`で登録された49 types、その各typeの公式 `validBlocks`、全関連blockstate/property/resource variants、公式renderer registration 26件と非登録23型を含む全専用・terrain・item・text/shader・particle/audio/light/UI/gameplay delegate、型別NBT field/update/load/event/renderer条件を母集合にする。現在は登録49・専用renderer26/非登録23と主要Client draw pathsを確認した段階で、validBlocksの全state/property展開、全NBT/events、別描画経路・consumer、assets/resourcesは未完。有限分母が閉じる前に互換率を算出しない。**将来の100%判定**は固定母集合全体を列挙し、source path根拠、expected output、NBT/state/event/resource/別描画経路の検査と必要なA/B動的比較が合格した場合のみ成立する。現在の達成率を意味せず、現状100%ではない。renderer未登録を除外して分母を狭めない。

完了には各条件について公式symbolとClient consumerのpath/行範囲、owner、NBT/state/event入力、期待出力、source確認範囲、必要なA/B比較結果が記録され、静的差分と別pipeline/texture合成/item/resource/particle/state consumerが監査済みであること。何らかの未確認consumer・resource variant・condition・比較caseが残れば100%とはしない。source登録網羅やdocs checkだけでは動作互換の証明にならない。
