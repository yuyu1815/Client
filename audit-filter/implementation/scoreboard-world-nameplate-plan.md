# BELOW_NAME world-space nameplate: render/font API investigation and minimal plan

Status: read-only investigation / plan only. No source, build output, or ledger was edited. `Client` source was only read. This plan uses the canonical consumer contract in `audit-filter/implementation/scoreboard-below-name-contract.md`; it does not consume LIST in-progress artifacts. No build/test command was run. This does not start implementation.

## Decision

There is no existing general world-space text/name-tag submission path in the inspected Client source. `BlockEntityPipeline` draws baked sign/block-entity **models/textures**, not sign text, and `MenuOverlayPipeline` is screen-space. The smallest plausible reuse is to reuse MenuOverlay's CPU Minecraft-font glyph/span preparation and glyph atlas data while adding a dedicated world-space billboard draw path that consumes the normal world depth attachment before the current explicit depth clear. Do not try to turn `MenuElement::TextSpans` into world text or draw nameplates through the normal HUD overlay.

Safe atlas sharing is **not available as an API today**: `MenuOverlayPipeline` owns private `mc_glyph_map`, `mc_font`, `mc_font_color`, and `tex_set`; the world pipeline cannot access them. The minimal safe extension is to extract/share a font-preparation resource/API whose ownership and reload lifetime are explicit, or make MenuOverlay own and invoke a distinct world draw path. Duplicating atlas allocations/loading is technically simpler to isolate but needlessly duplicates expensive resources and creates synchronization/reload drift. No `MenuOverlay` globals UBO should be reused for world transforms.

The exact Minecraft name-tag depth/see-through modes and their primary-source state are **not resolved by this repo inspection**. Do not invent the requested vanilla two-pass behavior, sneak behavior, or pass blend/depth flags from the current renderer. Verify those against the matching official version source/API before setting pipeline state. The contract document separately records vanilla component construction, selection, distances, ordering, scale, and attachment behavior from official evidence; follow it for those semantics.

## Existing builder and actual caller

- `pomme-client/src/ui/player_tab.rs:958-1004`, `PlayerNameplates` and `build_player_nameplates`: caller provides `EntityStore`, `TabList`, `Scoreboard`, local UUID, partial tick, GUI scale, camera position and `project` closure. It iterates living entities, requires `player_uuid` and tab-list presence, skips local UUID, interpolates `prev_position.lerp(position, partial_tick)`, offsets Y by 2.0 crouching / 2.3 standing, rejects beyond 32 / 64 blocks, projects to pixels, and emits centered `MenuElement::TextSpans` containing the team-formatted `Scoreboard::player_name(&player.name, None)`. A source comment explicitly calls it a screen-space approximation and lists missing world-billboard behavior.
- `pomme-client/src/app/phases/in_game.rs:2930-2944`: `in_game` is the real caller, conditional on `!benchmark_running && !game.hide_gui`. It passes `renderer.camera_render_position()` and `renderer.project_world_to_screen`. Thus the current player tags are assembled with HUD elements and rendered only by the menu overlay, not submitted with entity geometry/depth.
- `player_tab.rs` is also the current place building the player tab overlay; keep `build_player_tab_overlay` unchanged. Migration should remove/replace only the `build_player_nameplates` UI-element insertion/call, not alter tab-list score UI.
- Existing eligibility is players only: entity must have `player_uuid`, must not be local, and must exist in `TabList.players`. No generic non-player nameplate pass should be introduced as a side effect. Current GUI/benchmark gates should remain deliberate and be mapped into renderer submission data/state; `game.hide_gui` semantics need to be preserved.

## World pass, draw order, depth, and coordinates

- `pomme-client/src/renderer/mod.rs:1812-1824`: on `RenderMode::World`, constructs one `CameraUniform::new(&self.camera, ...)` and updates each world pipeline before command recording. A future world text draw must receive the same frame index and camera state, and prepare its per-frame data before the relevant draw call.
- `pomme-client/src/renderer/mod.rs:1973-2000`: main world selects `swapchain.render_pass` (unless main-menu blur), starts it with clear color and depth 1.0. `pomme-client/src/renderer/swapchain.rs:277-346`, `create_render_pass`, confirms a D32Sfloat depth attachment, clear-on-load, store-op DontCare. `framebuffers` share the swapchain depth view.
- `pomme-client/src/renderer/mod.rs:2000-2165+`: world geometry order is sky; solid/cutout chunks; item shadows; block-damage overlay; entities; block entities; item entities; particles; translucent water; clouds; weather; world border; chunk borders. There is a deliberate full depth clear immediately before held hand/item rendering (`mod.rs` around 2165-2175); hand/held draw follows. `MenuOverlayPipeline::draw` is much later (around 2240+), after held item, in the same render pass, and its UI draw follows overlay elements. Therefore a world-depth-tested tag must draw after the relevant world opaque/entity geometry but **before** that explicit hand depth clear. Exact placement among translucent/world-border work and any see-through pass must wait for verified intended semantics; rendering after the clear makes the world depth test ineffective.
- World positions use camera-relative precision, not raw large absolute f32. `renderer/camera.rs:491-503`, `CameraUniform`, stores view-projection, eye relative to an integer render anchor and integer anchor separately. `CameraUniform::new` at 523+ rebases in f64 before converting. `renderer/mod.rs:1067-1086`, `camera_render_position`, `camera_anchor`, and `project_world_to_screen`, plus world draw callers around 2054/2147, show the render camera offset and render anchor distinction. `BlockEntityPipeline::draw(cmd, frame, anchor, items)` at `pipelines/block_entity.rs:485-580` is an example of passing an anchor and building per-item transforms, but not text. World text vertices/anchor must follow the same anchor-relative convention (rebase DVec3 before f32) and use the camera view-projection/billboard basis; do not use `project_world_to_screen`.
- Frame order includes UI preparation in `in_game` before renderer execution; actual command draw is inside the world pass. The future input therefore needs to reach `Renderer`/`RenderMode::World`, not stay as `MenuElement`s. No existing nameplate render-record type was found; do not assume one exists.

## MenuOverlay font/glyph API and lifecycle

- `pomme-client/src/renderer/pipelines/menu_overlay.rs:82-161`: private `FontAtlas` / `build_font_atlas` is a separate Montserrat+icon atlas; not the Minecraft text atlas appropriate for styled Minecraft names/objectives.
- `MenuOverlayPipeline::new` at `menu_overlay.rs:262+` loads `GlyphMap::load(font_sources, font_layer_limit)`, stores `mc_glyph_map`, creates grayscale/color font texture resources (`create_font_textures`), binds them into private `tex_set` bindings 3 and 8, and keeps the renderer's private descriptor set/resources. There is no accessor/export API for map, images, views, sampler, or descriptor sets.
- `menu_overlay.rs:638-673`, `reload_minecraft_fonts`: reloads glyph map and gray/color images; updates descriptor bindings 3/8 then destroys/replaces old texture resources and updates `mc_glyph_map`. Its doc requires device idle because old textures are destroyed immediately. Renderer calls this at `renderer/mod.rs:1564+` in resource-pack reload flow. A second world descriptor set referencing the same atlas must be rebound before old images are destroyed, or share a stable common resource owner that updates all descriptors as one operation.
- `menu_overlay.rs:692-~1000`, `draw_from`: maps UI `MenuElement`s to glyph vertices on CPU; `TextSpans` calls private `push_text_into`. The method writes screen dimensions to one `globals_buffer` before building/writing vertices and records into one reusable `vertex_buffer`, then binds the menu pipeline/descriptor sets. `draw_from` can be called multiple times in one frame using `vertex_base` for blurred menu layers (not a world transform API). Reusing its screen globals for a world pass would overwrite the UBO; reusing the single mutable vertex buffer for multiple draws before consumption also needs careful range/recording semantics.
- `menu_overlay.rs:1586-1650`: public `spans_width`, `text_width`, and private `push_text_into`. `spans_width` reads `mc_glyph_map`; `push_text_into` takes `[TextSpan]`, `McTextDraw` pixel coordinates/scale, mutable output vertices and RNG. The text implementation covers multiple styled spans, glyph fonts, bold, inline objects, shadow/baked-sheet rendering and color glyphs (see `McTextSources`/`push_mc_text` around 4160+, and glyph emit around 4385+). This is good **CPU font/layout code to reuse**, but its current draw geometry is 2D pixel-space.
- `menu_overlay.rs:1648-1730`: `recreate_pipeline` only replaces menu pipeline objects; `destroy` releases its own descriptor pool/layout, vertex/globals buffers and owned images. `renderer/mod.rs:783-~910` handles resize by waiting/recreating swapchain and recreating pass-dependent pipelines; MenuOverlay has no resize-dependent atlas/UBO behavior but does recreate graphics pipelines for the new render pass. A separate nameplate pipeline must likewise recreate pipeline against the new swapchain render pass and clean up all descriptor/buffer/image ownership explicitly. A glyph mesh cached beyond a font/resource reload must be invalidated/rebuilt against the new glyph map/atlas.
- **UI UBO clobber hazard:** both normal menu draws and calls to `draw_from` write the same `globals_buffer` with `[screen_w, screen_h]` at method entry. No per-frame globals buffers are used there. World text must have a separate camera/world uniform descriptor/buffer (prefer existing `CameraUniform` layout and per-frame slot pattern from `BlockEntityPipeline`), so menu overlay's later UI draw does not mutate world projection inputs. Existing world pipelines allocate per-frame camera descriptor sets/buffers (`MAX_FRAMES_IN_FLIGHT`); mirror that lifetime pattern. Descriptor sets must never refer to replaced atlas images after font reload.

## Minimal implementation plan (not implementation)

1. Keep the contract data resolution separate from rendering. Resolve per-player BelowName component per `scoreboard-below-name-contract.md`: BELOW_NAME objective; score by raw profile name; no label on missing objective/score; value format precedence score > objective > NO_STYLE; final spans are score + space + objective display title. Keep existing ordinary team-formatted player name label and exact contract-selected anchor/order/visibility. Avoid making guessed Rust model types; audit the exact currently staged scoreboard model before implementing any accessor.
2. Replace only the UI nameplate builder output with render submission data. A CPU preparation helper should output a record containing resolved local-space anchor inputs and styled line/span data for the existing eligible player only, not screen x/y `MenuElement`s. For naming/signatures/types, inspect canonical contract and current source at implementation time; this report proposes no unverified Rust type identifiers.
3. Extract the smallest reusable CPU glyph preparation from `MenuOverlayPipeline::push_text_into` / `push_mc_text` so it can write style-rich local 2D glyph quads for spans into a supplied vertex vector without using screen-global coordinates. Convert that local 2D mesh into a world billboard at each anchor using camera-right/up basis and vanilla world scale (the contract specifies `NAMETAG_SCALE` 0.025); keep geometry camera-facing, with width centered and deterministic baseline/line spacing. Pass camera-relative anchor into GPU transform or CPU bake after DVec3 rebasing. Do not reduce rich spans to a plain string.
4. Add a dedicated world draw path/pipeline only after verifying target-version vanilla pipeline semantics for ordinary/depth/see-through passes. It needs world camera projection, alpha blend, depth attachment behavior, atlas sampling, per-frame GPU-safe vertex/uniform resources, and explicit recreation/destruction. Consider reuse of font atlas through a shared owner or method with clear descriptor rebinding; do not reach into private MenuOverlay state ad hoc and do not share its mutable screen UBO. If exact vanilla requires two label passes, implement only after official primary verification; no pass state is prescribed by this plan.
5. Build and update nameplate world records during frame prep; issue draw in `RenderMode::World` after relevant world geometry/entities and before the hand-pass depth clear, respecting existing hide-GUI/benchmark checks. Make MenuOverlay draw operate as before. Remove the nameplate `MenuElement::TextSpans` emission/caller so one label cannot appear in both paths. Keep player filters as-is initially; do not affect non-player entities.
6. Add pure CPU checks for component/span construction and billboard transform math, plus a render integration check for occlusion/depth ordering, camera anchor rebasing, resize pipeline recreation, resource reload descriptor rebinding, and no duplicate HUD/world label. The canonical contract's required score-selection/format cases and strict 10-block boundary remain authoritative; don't fabricate vanilla see-through/sneak results.
